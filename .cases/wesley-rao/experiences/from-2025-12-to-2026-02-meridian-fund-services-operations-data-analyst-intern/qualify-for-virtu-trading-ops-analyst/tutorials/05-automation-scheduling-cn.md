# 教程 05：自动化与每日调度（cron / APScheduler 把对账脚本化）

> 对应 POC-05，难度标记 🟠 Nice-to-have（加分项，不是硬门槛）。
>
> JD 里对应这句话：**"work closely with software engineers to further automate operational workflows"**（和软件工程师紧密合作，进一步把运营流程自动化）。
>
> 这篇教程假设你已经有一个能跑的对账（reconciliation）项目：跑在 PostgreSQL 上，用 SQL 找出"内部账 vs 托管行账"对不平的 break。我们要给它加一层：**让它每天凌晨到点自己跑，不用你手动点。**

---

## 0. 先说清楚这篇教程要解决什么问题

假设你现在的对账流程是这样的：

1. 早上到公司，打开电脑。
2. 手动跑一段 SQL，把昨天的内部账和托管行账对一遍。
3. 找出对不平的 break，记到一个"台账"（break ledger，就是记录所有待处理差异的表）里。
4. 然后开始一个一个查。

这里面有个很烦的事：**第 1 到第 3 步是纯机械劳动**。每天都一样，早跑晚跑结果都一样，跑得越早你越早能开始真正动脑子的部分（追 break）。

那能不能让电脑在你还没到公司的时候（比如凌晨 6 点）就自动把第 1 到 3 步跑完？这样你一到岗，台账里已经躺着一份"今天要处理的 break 清单"了。

这就是**任务调度 / 定时任务（scheduling）**要干的事。

> 💡 你可能会问：这跟我直接写个脚本手动运行有什么区别？
>
> 区别在于"到点自动"这四个字。脚本是"你喊它才动"，调度是"它自己看表，到点就动，你人不在也照跑"。对账最典型的场景就是凌晨批处理，那个点没人会守在电脑前。

## 1. 什么是"定时任务 / 调度"？用闹钟来类比

最简单的理解：**定时任务就是给电脑上的某段程序设一个闹钟。**

- 你手机闹钟：设"每天 7:00 响" → 到 7:00，手机自己响，不用你管。
- 定时任务：设"每天 6:30 跑对账脚本" → 到 6:30，电脑自己跑那段脚本，不用你管。

区别只是：闹钟到点是"发出声音"，定时任务到点是"执行一段代码"。

调度系统（scheduler）就是那个"一直盯着表、到点触发动作"的东西。它自己不干活，它只负责"看表 + 到点喊人干活"。真正干活的是你写的那段对账代码。

这里有两个角色，一定要分清楚：

| 角色 | 是谁 | 干什么 |
|------|------|------|
| 调度器（scheduler） | cron 或 APScheduler | 看表，到点触发 |
| 任务（job / task） | 你的对账函数/脚本 | 跑 SQL，刷新台账 |

后面我们会讲两种调度器：**cron** 和 **APScheduler**。它们都是"看表的那个角色"，只是一个是操作系统层面的，一个是 Python 代码层面的。

## 2. cron 是什么？Linux 世界的"系统级闹钟"

### 2.1 一句话定义

**cron 是 Linux/Mac 系统自带的一个后台服务，专门负责"到点运行命令"。** 你告诉它"几点几分跑哪个命令"，它就记下来，到点替你跑。

它一直在后台默默运行（这个后台服务叫 `crond`，d 是 daemon 守护进程的意思）。你不用管它，它自己看系统时钟。

你要做的，就是往一张叫 **crontab**（cron table，cron 的时间表）的清单里写一行，告诉它"什么时候、跑什么"。

### 2.2 一行 cron 长什么样

一条 cron 规则就是一行文本，长这样：

```
30 6 * * *  /usr/bin/python3 /home/wesley/recon/run_recon.py
```

拆开看，它分成两大块：

- **前面 5 个字段** `30 6 * * *` → 决定"什么时候跑"（时间表达式）
- **后面一串** `/usr/bin/python3 /home/wesley/recon/run_recon.py` → 决定"跑什么"（要执行的命令）

后面那串命令没什么玄机，就是你在终端里手敲会用的那条命令（用绝对路径，原因后面讲）。真正需要学的是**前面那 5 个字段**，也就是所谓的 **cron 表达式**。

### 2.3 cron 表达式：5 个字段逐个讲

那 5 个字段，从左到右分别是：

```
┌───────────── 分钟 minute       (0 - 59)
│ ┌─────────── 小时 hour         (0 - 23，24小时制)
│ │ ┌───────── 日   day of month (1 - 31)
│ │ │ ┌─────── 月   month        (1 - 12)
│ │ │ │ ┌───── 星期 day of week  (0 - 6，0 是周日)
│ │ │ │ │
30 6 * * *
```

每个字段可以填：

- **一个具体数字**：`30` 表示"第 30 分" / `6` 表示"6 点"。
- **星号 `*`**：表示"每一个都算，不挑"。比如日期那位填 `*`，就是"每天都行，不挑日子"。
- **逗号列举**：`1,15` 表示"1 号和 15 号"。
- **横杠范围**：`1-5`（在星期那位）表示"周一到周五"。
- **斜杠步长**：`*/15`（在分钟那位）表示"每隔 15 分钟"。

把这 5 个字段拼起来读，就是一句"什么时候"。

### 2.4 几个真实例子，逐个翻译成人话

```
30 6 * * *
```
读法：分=30，时=6，日=*，月=*，周=*。
翻译：**每天早上 6:30 整，跑一次。**（日/月/周都是 `*`，所以不挑日子、不挑月份、不挑星期，天天跑。）

```
0 2 * * *
```
翻译：**每天凌晨 2:00 整跑一次。** 这是很典型的"夜里批处理"时间点。

```
0 6 * * 1-5
```
翻译：**周一到周五，每天早上 6:00 跑一次**（周末不跑）。对账通常只在交易日跑，周末市场不开，`1-5` 正好排除周末。注意这还不够精确，法定假日市场也不开，纯 cron 表达式表达不了"假日不跑"，得在代码里再判断一次（后面 §6 会讲）。

```
*/15 9-17 * * 1-5
```
翻译：**工作日的 9 点到 17 点之间，每隔 15 分钟跑一次。** 适合"盘中每 15 分钟刷新一次实时对账"这种场景。

```
0 0 1 * *
```
翻译：**每月 1 号的 0 点跑一次**（月度对账）。

> ⚠️ 常见坑：星期字段的 `0` 是周日，不是周一。不同系统偶尔有差异（有的把 7 也当周日），配之前最好查一下你机器上的约定，或者干脆用 `1-5` 这种明确范围，别赌。
>
> ⚠️ 另一个坑：cron 的时间用的是**服务器所在时区**，不是你本地时区。如果服务器设的是 UTC，你写 `30 6` 实际是 UTC 6:30，不是你美东的 6:30。上线前一定确认服务器时区（`timedatectl` 或 `date` 命令能看）。

> 💡 你可能会问：这些表达式我记不住怎么办？
>
> 不用背。有个网站叫 crontab.guru，你把表达式贴进去，它用英文告诉你这是"什么时候"。日常写 cron 基本都靠它验证，没人靠脑子硬记。

### 2.5 怎么把这行加进去

在终端敲：

```bash
crontab -e
```

这会打开你的 crontab 文件（你个人的时间表），你把那一行加进去，存盘退出，就生效了。cron 会自动读取。

用 `crontab -l` 可以列出当前所有已经设好的 cron 任务，检查一下有没有加成功。

## 3. APScheduler 是什么？Python 代码里的"闹钟"

### 3.1 一句话定义

**APScheduler（Advanced Python Scheduler）是一个 Python 库，让你在自己的 Python 程序里排定时任务。**

跟 cron 的最大区别：

- **cron** 是操作系统层面的。它是系统的一部分，触发的是"命令行命令"。你的对账逻辑对它来说是个黑盒（它只知道"跑这条命令"）。
- **APScheduler** 是你 Python 程序内部的。它触发的是"你代码里的一个函数"。整个调度逻辑写在你的 Python 代码里，跟你的对账代码住在同一个程序里。

打个比方：

- cron 像是**请物业帮你定闹钟**：物业系统统一管，稳定可靠，但你只能让它"到点去敲某个门"，门后面发生什么它不掺和。
- APScheduler 像是**你自己房间里放个闹钟**：闹钟和你在同一个房间，到点它能直接递给你东西、跟你互动，非常灵活，但前提是"你这个房间（Python 程序）得一直开着灯"（进程得一直活着）。

### 3.2 什么时候用哪个？（这是面试可能会问的判断题）

| 情况 | 更适合 | 为什么 |
|------|------|------|
| 就是"每天凌晨跑一个脚本" | **cron** | 简单、系统级、进程不用常驻，最省心 |
| 已经有一个长期运行的 Python 服务/程序 | **APScheduler** | 调度逻辑直接写在程序里，能读程序内部状态 |
| 需要动态改时间、运行中增删任务 | **APScheduler** | cron 改时间要改 crontab，代码里改更灵活 |
| 团队/生产环境标准就是 cron 或 Airflow | **跟团队走** | 别自己发明，运维要能统一管 |
| 需要复杂依赖（A 跑完才跑 B、失败重试链） | 都不太够，考虑 **Airflow** | cron/APScheduler 是"单点闹钟"，编排复杂 DAG 不是强项 |

对你这个"每天凌晨跑一次对账"的场景，**说实话 cron 就够了**，而且更省心。但这篇教程主要用 APScheduler 写完整例子，原因有两个：

1. APScheduler 是纯 Python，你能把"调度 + 对账逻辑 + 幂等 + 日志"全写在一个文件里，读起来完整、好理解。
2. 面试里能讲清"我知道两种，且知道该在什么时候选哪个"，比只会一种更值钱。

> 💡 你可能会问：那生产上真跑的时候到底用哪个？
>
> 现实里的团队，小任务多半用 cron（甚至云上的 cron 服务），复杂管道用 Airflow（后面 §7 会提到，它是上游 IT 常用的东西）。APScheduler 更多用在"我这个 Python 服务本身需要内建定时"的场景。所以最诚实的答案是：**理解调度这件事本身，比纠结具体用哪个工具重要。** 面试官想听的是你懂取舍。

## 4. 完整可运行例子：用 APScheduler 每天定时跑对账

我们分三层来写，从里到外：

1. 最里层：真正干活的函数（跑对账 SQL + 刷新台账）。
2. 中间层：把干活函数包一层（加日志、加幂等、加异常处理）。
3. 最外层：APScheduler，负责"每天 6:30 触发中间层"。

### 4.1 先装库

```bash
pip install apscheduler psycopg2-binary
```

- `apscheduler`：调度器本体。
- `psycopg2-binary`：Python 连 PostgreSQL 的驱动（你的对账数据在 PG 里）。

### 4.2 完整代码（先整体看一遍，再逐行拆）

```python
# run_recon_scheduled.py
import logging
import datetime
import psycopg2
from apscheduler.schedulers.blocking import BlockingScheduler

# ---------- 第 0 步：配置日志 ----------
logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(message)s",
    handlers=[
        logging.FileHandler("recon.log"),   # 写进文件，方便事后查
        logging.StreamHandler(),             # 同时打在屏幕上
    ],
)
logger = logging.getLogger("recon")

DB_DSN = "host=localhost dbname=trading user=wesley password=***"


# ---------- 第 1 层：真正干活的函数 ----------
def run_reconciliation(as_of_date):
    """
    对某一天(as_of_date)的账做对账：
    找出内部账 vs 托管行账对不平的 break，写进 break 台账。
    """
    conn = psycopg2.connect(DB_DSN)
    try:
        cur = conn.cursor()

        # 幂等关键点：先删掉这一天已经写过的 break，再重算重写。
        # 这样同一天重复跑，结果只会有一份，不会越跑越多。
        cur.execute(
            "DELETE FROM break_ledger WHERE as_of_date = %s",
            (as_of_date,),
        )

        # 核心对账 SQL：内部账 full outer join 托管行账，
        # 金额对不上或一边缺失的，就是 break。
        cur.execute(
            """
            INSERT INTO break_ledger
                (as_of_date, account, break_type, internal_amt, custodian_amt)
            SELECT
                %s AS as_of_date,
                COALESCE(i.account, c.account) AS account,
                CASE
                    WHEN i.account IS NULL THEN 'MISSING_INTERNAL'
                    WHEN c.account IS NULL THEN 'MISSING_CUSTODIAN'
                    ELSE 'AMOUNT_MISMATCH'
                END AS break_type,
                i.amount AS internal_amt,
                c.amount AS custodian_amt
            FROM internal_positions i
            FULL OUTER JOIN custodian_positions c
                ON i.account = c.account
               AND i.as_of_date = c.as_of_date
            WHERE COALESCE(i.as_of_date, c.as_of_date) = %s
              AND (
                  i.account IS NULL
                  OR c.account IS NULL
                  OR i.amount <> c.amount
              )
            """,
            (as_of_date, as_of_date),
        )

        break_count = cur.rowcount
        conn.commit()
        logger.info("对账完成：%s 共写入 %d 条 break", as_of_date, break_count)
        return break_count
    finally:
        conn.close()


# ---------- 第 2 层：包一层，负责日志/异常，方便调度器调用 ----------
def recon_job():
    """调度器每天到点就调用这个函数。"""
    # 对账的是"昨天"的账（今天凌晨跑，处理的是昨天收盘的数据）
    as_of = datetime.date.today() - datetime.timedelta(days=1)

    # 交易日判断：周末不跑（周六=5, 周日=6）
    if as_of.weekday() >= 5:
        logger.info("%s 是周末，跳过对账", as_of)
        return

    logger.info("===== 开始每日对账 as_of=%s =====", as_of)
    try:
        n = run_reconciliation(as_of)
        logger.info("===== 对账成功，%d 条 break 待处理 =====", n)
    except Exception:
        # 出错不能让调度器整个崩掉，记下完整堆栈，等人来看
        logger.exception("对账失败！需要人工检查")


# ---------- 第 3 层：APScheduler，负责"到点触发" ----------
if __name__ == "__main__":
    scheduler = BlockingScheduler(timezone="America/New_York")

    # 每天早上 6:30 触发 recon_job（等价于 cron 的 "30 6 * * *"）
    scheduler.add_job(
        recon_job,
        trigger="cron",
        hour=6,
        minute=30,
        id="daily_recon",
    )

    logger.info("调度器启动，等待每天 6:30 触发对账。按 Ctrl+C 退出。")
    scheduler.start()   # 这一行会阻塞住，程序就一直在这守着看表
```

### 4.3 逐行拆解

**第 0 步：日志配置**

```python
logging.basicConfig(level=logging.INFO, ...)
```

自动化任务最怕的就是"凌晨 3 点它悄悄挂了，早上你还不知道"。所以日志是刚需，不是可选项。这里我们配了：

- `level=logging.INFO`：记录 INFO 级别以上的信息（正常流程 + 警告 + 错误都记）。
- `format=...`：每行日志前面自动加时间戳和级别，出问题能看清"几点几分发生了什么"。
- 两个 handler：一个写进 `recon.log` 文件（事后翻查），一个打在屏幕上（当场能看到）。

**第 1 层：`run_reconciliation`**

这是真正干活的地方。三件事：

1. 连 PostgreSQL。
2. `DELETE ... WHERE as_of_date = %s`：**先删掉这一天已有的 break**。这一句是幂等的关键，下一节 §5 专门讲。
3. `INSERT ... SELECT ...`：跑对账 SQL，把 break 重新算出来写进台账。用 `FULL OUTER JOIN` 是为了"两边缺一边"的情况也能抓到（内部账有、托管行没有，反过来也一样）。

`%s` 是参数占位符，值通过后面的元组传进去（这是防 SQL 注入的正确写法，绝对不要用字符串拼接把日期拼进 SQL）。

`try / finally` 保证不管成功失败，最后都会 `conn.close()` 把数据库连接关掉，不泄漏连接。

**第 2 层：`recon_job`**

这是调度器直接调用的函数，它把"业务判断 + 异常兜底"包在外面：

- 算出 `as_of`（要对账的日期 = 昨天）。为什么是昨天？因为你凌晨跑的时候，处理的是昨天收盘后的数据。
- 周末判断：`as_of.weekday() >= 5` 就跳过（这是 cron 表达式做不到的精细判断，放代码里）。
- `try / except Exception` + `logger.exception(...)`：**这是自动化任务的救命符。** 如果对账里抛了异常（比如数据库连不上），我们不让整个调度器崩掉，而是把完整错误堆栈写进日志，等你早上来看。`logger.exception` 会自动带上堆栈，比 `logger.error` 更适合排错。

> ⚠️ 常见坑：新手常把干活逻辑直接扔给调度器，不包异常。结果某天 SQL 报错，异常往上冒，把整个调度进程干掉了，从此以后每天都不跑了，而你完全不知道。**调度的任务函数一定要自己吞掉异常并记日志**，让"这一次失败"不影响"下一次还能跑"。

**第 3 层：APScheduler**

```python
scheduler = BlockingScheduler(timezone="America/New_York")
```

`BlockingScheduler` 是最简单的一种：它启动后会"阻塞"当前程序，程序就停在那儿一直守着看表。适合"这个程序就专门用来跑调度"的场景。（还有 `BackgroundScheduler`，它在后台线程跑，适合"我程序还有别的事要干，顺便挂个定时"。）

`timezone="America/New_York"` 明确指定时区，避免前面说的"服务器 UTC 时间坑"。

```python
scheduler.add_job(recon_job, trigger="cron", hour=6, minute=30, id="daily_recon")
```

- `recon_job`：到点要调用的函数。
- `trigger="cron"`：用 cron 风格的触发规则（APScheduler 也支持 `interval` 每隔多久、`date` 只跑一次）。
- `hour=6, minute=30`：每天 6:30。注意这其实就是 cron 的 `30 6 * * *`，只是写成了 Python 参数。
- `id="daily_recon"`：给这个任务起个名字，方便后面查看/删除。

```python
scheduler.start()
```

启动。程序从这里开始"守着看表"，到 6:30 自动调 `recon_job`。

### 4.4 等价的 cron 方案（对照）

如果不用 APScheduler，改用系统 cron，你只需要：

第一步，把上面代码简化成"跑一次就退出"的脚本（去掉第 3 层的 scheduler，`__main__` 里直接调 `recon_job()`）：

```python
# run_recon_once.py
if __name__ == "__main__":
    recon_job()   # 跑一次就结束，不守着
```

第二步，`crontab -e` 加一行：

```
30 6 * * 1-5  /usr/bin/python3 /home/wesley/recon/run_recon_once.py >> /home/wesley/recon/cron.log 2>&1
```

逐段读这行：

- `30 6 * * 1-5`：工作日早上 6:30。
- `/usr/bin/python3 /home/wesley/recon/run_recon_once.py`：用绝对路径跑脚本。
- `>> ... cron.log 2>&1`：把脚本的所有输出（正常的 `>>` 和错误的 `2>&1`）都追加到 cron.log 里。**这一段很重要**，因为 cron 跑的时候没有屏幕，输出不重定向到文件就全丢了，出问题你无从查起。

> ⚠️ 常见坑（cron 专属）：cron 运行时的环境跟你终端里完全不一样，它几乎没有环境变量，`PATH` 都可能是空的。所以：
> - 命令一律用**绝对路径**（`/usr/bin/python3` 而不是 `python3`）。
> - 脚本里读的环境变量（比如数据库密码）在 cron 环境里可能读不到，要么在 crontab 顶部显式设，要么用配置文件。
> - 别指望"我终端里能跑，cron 里就能跑"。八成第一次跑不起来，就是环境变量/路径的问题。先看 cron.log。

对比一下两种写法，你会发现：**"每天 6:30 跑"这个意思，cron 用一行表达式，APScheduler 用几行 Python，本质一模一样。** 差别在于 cron 更省事，APScheduler 更能跟你的代码融为一体。

## 5. 幂等性（idempotency）：同一天重复跑，不会重复记账

这是自动化里最容易被新手忽略、但一旦出事就很尴尬的点，单独拿出来讲。

### 5.1 用大白话解释什么是幂等

**幂等 = 同一件事做一次和做很多次，结果一样。**

生活例子：电梯的"上行"按钮。你按一次，它记住"要往上"。你连按十次，结果还是"往上"，不会变成"要上十层"。这就是幂等。

反例：ATM"取 100 块"这个动作**不幂等**。做一次扣 100，做三次扣 300，结果不一样。

### 5.2 为什么对账必须幂等

想象一个真实事故：

- 凌晨 6:30，对账正常跑了，往台账里写了 20 条 break。
- 结果因为网络抖动，你以为它没跑成功，手动又跑了一次。
- 如果代码是"每次都往台账里 INSERT"，那台账里现在有 **40 条**（20 条重复的）。
- 你早上一看：怎么 40 个 break？其实真实只有 20 个。**假的工作量、假的告警、白白追查。**

所以对账脚本必须做到：**这一天不管跑几次，台账里"这一天的 break"永远只有正确的那一份。**

### 5.3 怎么实现幂等

我们代码里已经做了，就是那句：

```python
cur.execute("DELETE FROM break_ledger WHERE as_of_date = %s", (as_of_date,))
```

**先删掉"这一天"已有的 break，再重新算、重新写。** 这样跑一次是这份结果，跑十次还是这份结果，完全幂等。这叫 "delete-then-insert"（先删后插）模式，是批处理里最常用、最好理解的幂等做法。

> 💡 你可能会问：还有别的做法吗？
>
> 有。比如 PostgreSQL 的 `INSERT ... ON CONFLICT DO UPDATE`（俗称 upsert，有则更新无则插入），或者给台账加唯一约束让重复插入直接被拒。但对你这个场景，"先删后插"最直观、最不容易出错，先掌握这个就够了。

> ⚠️ 常见坑：删除范围一定要正好圈住"这一次要重算的数据"，不能多删也不能少删。这里我们按 `as_of_date` 删，正好是"这一天"，不会误伤别的日期的 break。如果你删条件写错（比如漏了 WHERE），可能把整张台账清空，那就是生产事故了。

## 6. 几个真实但常被忽略的工程点

自动化不是"写完能跑就完事"。下面这几点，是"能跑"和"敢让它无人值守跑半年"之间的差距。

### 6.1 日志（logging）：出了问题怎么查

前面代码已经配了日志，这里补充"为什么"和"记什么"：

- **无人值守 = 你不在现场。** 出了任何问题，你唯一的线索就是日志。日志写得好，五分钟定位；写得差，抓瞎。
- 每次运行至少记：开始时间、处理的是哪天、写了多少条 break、成功还是失败、失败的完整堆栈。
- 日志要写文件（`recon.log`），别只打屏幕。凌晨跑的时候没人看屏幕。
- 日志文件会越长越大，生产上要配"日志轮转"（logrotate 或 Python 的 `RotatingFileHandler`），否则几个月后一个几 GB 的日志文件能把磁盘撑满。

### 6.2 失败重试

数据库偶尔会连不上（网络抖一下），这种"临时性失败"重试一下往往就好了。简单加个重试：

```python
import time

def run_reconciliation_with_retry(as_of_date, max_retries=3):
    for attempt in range(1, max_retries + 1):
        try:
            return run_reconciliation(as_of_date)
        except psycopg2.OperationalError as e:
            # OperationalError 通常是连接类的临时问题，值得重试
            logger.warning("第 %d 次尝试失败：%s，5 秒后重试", attempt, e)
            time.sleep(5)
    logger.error("重试 %d 次仍失败，放弃", max_retries)
    raise RuntimeError("对账重试耗尽")
```

要点：

- **只重试"临时性"错误**（连接超时、网络抖动这类 `OperationalError`）。
- **不要盲目重试所有错误**。如果是 SQL 写错了（逻辑 bug），重试一百次也还是错，只是浪费时间、刷屏日志。这种要让它直接失败、报警、等人来改。
- 重试之间要 `sleep` 一下（比如 5 秒），别瞬间连着重试三次，那跟没重试差不多。

> 💡 你可能会问：重试和幂等有什么关系？
>
> 关系很大。**正因为对账是幂等的（§5），重试才安全。** 如果第一次跑到一半失败了、写了一半数据，重试时那句"先删后插"会把半截数据清掉重来，不会留下脏数据。**幂等是重试的安全垫。** 这两个点是配套的，面试里能把它们串起来讲，很加分。

### 6.3 依赖等待："源数据文件还没到，先别跑"

这是运营岗最真实的痛点，务必理解。

你的对账要用到"托管行发来的账"。托管行的数据通常是**每天定时把一个文件（比如 CSV）传到某个目录**，再由上游 IT 的管道导进数据库。问题是：**这个文件到得早不早、准不准时，不由你说了算。**

如果你死板地"6:30 一到就跑对账"，但托管行的文件今天 6:45 才到，那你 6:30 跑的时候，托管行那边的数据还是昨天的甚至是空的，**对出来的 break 全是假的**。

正确做法：**别只看钟点，还要看"数据到了没"。** 两种常见思路：

**思路 A：跑之前先检查数据就绪**

```python
def custodian_data_ready(as_of_date):
    """检查托管行今天的数据是否已经进库"""
    conn = psycopg2.connect(DB_DSN)
    try:
        cur = conn.cursor()
        cur.execute(
            "SELECT COUNT(*) FROM custodian_positions WHERE as_of_date = %s",
            (as_of_date,),
        )
        count = cur.fetchone()[0]
        return count > 0
    finally:
        conn.close()
```

然后在 `recon_job` 里，跑对账前先问一句"数据到了没"，没到就等一会儿再看（轮询），或者干脆跳过、记日志、报警。

**思路 B：由上游管道来"触发"你**

更成熟的做法是：不由你定时"猜"数据到没到，而是**上游 IT 的管道在把托管行数据导完之后，主动触发你的对账**。也就是把"对账"作为管道里数据导入步骤的**下一步**串进去。这样天然就没有"数据没到就跑"的问题，因为对账只会在"数据导完"之后才被触发。

思路 B 正是 JD 那句 "work closely with software engineers to further automate operational workflows" 的落点，下一节展开。

> ⚠️ 常见坑：初学者最容易犯的自动化错误，就是"只信钟表、不信数据"。凌晨批处理里，数据晚到、数据格式变了、上游管道今天挂了，都是家常便饭。**一个负责任的自动化任务，跑之前一定要先确认"我依赖的输入真的就绪了"。**

## 7. 哪些该自动化、哪些必须留给人（面试重点）

这一节内容不长，但可能是**整篇教程里面试最爱问的点**。因为它考的不是你会不会写 cron，而是你对"运营岗自动化的边界"有没有判断力。

### 7.1 一条清晰的分界线

| 步骤 | 该不该自动化 | 为什么 |
|------|------|------|
| 到点跑对账 SQL | ✅ 自动 | 纯机械，每天一样 |
| 找出 break | ✅ 自动 | 规则明确（金额对不上就是 break） |
| 给 break 初步分类（缺内部账/缺托管行账/金额差） | ✅ 自动 | 规则可枚举，机器分得清 |
| 刷新 break 台账 | ✅ 自动 | 数据搬运，无需判断 |
| **判断这个 break 严不严重、要不要立刻追** | ❌ 留给人 | 需要业务上下文和风险判断 |
| **决定怎么追、找谁核对、怎么跟托管行沟通** | ❌ 留给人 | 涉及沟通、协商、经验 |
| **判断"这是真差异还是数据延迟造成的假 break"** | ❌ 留给人 | 需要经验直觉 |

### 7.2 一句话总结这个边界

**机械的、规则明确的、每天一样的部分 → 交给机器。需要判断、需要上下文、需要沟通、要担责任的部分 → 留给人。**

自动化的价值不是"取代人"，而是"**把人从机械劳动里解放出来，让人专心做机器做不了的判断**"。

在你这个对账场景里，理想状态是：

- 机器在你到岗前，已经把"今天有哪些 break、分别是什么类型"整整齐齐摆在台账里。
- 你一到岗，跳过所有找 break 的机械活，**直接从"这些 break 里哪个最要紧、我先追哪个"开始**。而这正是机器做不了、需要你这个 Ops Analyst 动脑子的部分。

> 💡 你可能会问：面试官为什么爱问这个？
>
> 因为运营岗最怕两种人：一种是"什么都手动、不会自动化"，效率低；另一种是"什么都想全自动、包括判断"，会把风险判断也交给脚本，出大事。他们想找的是**知道边界的那种人**：能把机械活自动化，又清楚哪些判断必须人来担。你能主动讲出这条边界，就是在证明你有这个判断力。

## 8. 和上游 IT 数据管道协作（JD 的核心落点）

JD 那句 "work closely with software engineers to further automate operational workflows"，翻译成大白话就是：**你的对账不是孤岛，它挂在一条更长的数据管道上，而这条管道是软件工程师维护的。你得知道怎么跟他们对接。**

### 8.1 先搞清楚整条管道长什么样

一条典型的对账相关数据管道，大致是这样一串：

```
托管行/交易系统 -> 落地文件(CSV/文件到达某目录)
      -> 上游 IT 的管道把文件导入 PostgreSQL(数据入库)
            -> 【你的对账在这里】跑 SQL 找 break、刷新台账
                  -> 下游: 台账供你和团队处理 break
```

你的调度层，**串在"数据入库"和"人工处理"之间**。理解这一点，你才知道自己该在哪一环插进去、该跟谁对接。

### 8.2 跟工程师协作，具体要对齐三件事

**第一件：文件何时落地（时间契约）**

你得跟工程师问清楚：托管行的数据大概几点能导进库？是每天固定 6:00 前一定进库，还是"看情况"？

- 如果有明确的"6:00 前一定进库"承诺，你的对账排在 6:30 就比较稳。
- 如果时间不稳定，那你就不能只靠定时，得用 §6.3 的"数据就绪检查"或"由管道触发"。
- 这个对齐结果，直接决定你的调度该怎么设计。

**第二件：格式变更如何通知（变更契约）**

托管行的文件格式（列名、列顺序、日期格式）哪天可能会变。如果上游改了格式、导进来的数据结构变了，你的对账 SQL 可能悄无声息地对错、甚至直接报错。

所以要跟工程师约定：**上游数据结构一旦要变，得提前通知我，最好走一个变更评审流程。** 你这边也要在对账里加"数据体检"（比如检查行数是否异常为 0、关键字段是否为空），一旦上游偷偷改了导致数据不对，你的日志/告警能第一时间发现，而不是等对出一堆假 break 才察觉。

**第三件：调度串在管道哪一步（编排契约）**

这是最能体现"和工程师协作自动化"的地方。有两种对接层次：

- **松耦合（你先能做到的）**：你的对账用自己的 cron/APScheduler，排在一个"预计数据已入库"的时间点，跑之前自己检查数据就绪。你和管道各管各的，靠时间和检查来协调。
- **紧耦合（进阶，和工程师一起做）**：把你的对账**注册成上游管道的一个下游步骤**。上游 IT 很可能用的是 Airflow（一个专门编排数据管道的工具，把每一步画成一张有向图 DAG）。工程师可以在 Airflow 里，把"托管行数据导入完成"这个节点的下一步，直接接上"跑对账"。这样对账天然在"数据导完之后"才触发，彻底消灭"数据没到就跑"的问题。

> 💡 你可能会问：我一个大四生，面试时该怎么讲这段才不露怯？
>
> 你不需要真的会搭 Airflow。你要展示的是**思路和协作意识**。可以这么说：
>
> "我的对账现在是用 cron 独立跑的，排在预计数据入库之后，并且跑之前会检查托管行数据是否就绪。但我知道更稳的做法是把它接进上游的编排管道。如果团队用 Airflow，就把对账作为数据导入任务的下游节点，由管道来触发，而不是我自己猜时间。这块我会想跟维护管道的工程师一起对齐：文件落地时间、格式变更怎么通知、以及怎么把对账挂进现有的调度里。"
>
> 这段话就同时踩中了 JD 的 "automate operational workflows" 和 "work closely with software engineers" 两个点，还顺带证明了你懂 §6.3 的依赖等待、§8.2 的三个协作契约。这就是加分项 POC-05 想让你拿到的东西。

## 9. 小结与自查清单

这篇讲了：

- **调度是什么**：给程序设闹钟，到点自动跑（§1）。
- **cron**：系统级闹钟，一行表达式（分 时 日 月 周）搞定"什么时候"（§2）。
- **APScheduler**：Python 里的闹钟，调度逻辑写在代码里，灵活（§3）。
- **完整例子**：从对账函数 -> 日志/异常包装 -> APScheduler 触发，以及等价的 cron 写法（§4）。
- **幂等**：先删后插，同一天跑几次结果都一样（§5）。
- **工程细节**：日志、失败重试、数据就绪等待（§6）。
- **自动化边界**：机械活给机器，判断留给人（§7）。
- **和上游管道协作**：时间契约、变更契约、编排契约（§8）。

学完你应该能回答这几个自查问题（也是面试可能问的）：

1. cron 表达式 `30 6 * * 1-5` 是什么意思？（工作日早上 6:30）
2. cron 和 APScheduler 该怎么选？（简单脚本用 cron，需要跟代码融合/动态调整用 APScheduler；复杂管道上 Airflow）
3. 为什么对账脚本必须幂等？怎么做到？（避免重复记账；先删后插）
4. 对账里哪些能自动、哪些要留给人？（找 break/分类能自动；追不追、怎么追留给人）
5. 你的调度怎么跟上游 IT 的数据管道对接？（对齐落地时间、格式变更通知、把对账挂进编排；跑之前先确认数据就绪）

只要这五个问题你能用自己的话讲顺，POC-05 这个加分项就拿到手了。
