# Feed 排序微服务

> 时间：2026-06 到 2026-09。公司：Pulse Social。岗位：软件工程实习生，后端团队。行业：消费社交。

## 1. 背景

Pulse Social 是一家 200 人规模的消费社交产品，月活大概 800 万。Home Feed 是在一个 Python 单体里长出来的，排序逻辑、拉取逻辑、审核逻辑全部纠缠在一起。高峰期延迟尖刺很常见，p99 在 220ms 上下，团队想上一个新的排序模型基本要花好几天才能发布出去。

后端 Tech Lead 想把排序部分从单体里抽出来，做成一个干净的微服务。计划是用 Go 写，把候选生成、排序、后处理切成可组合的阶段，对外暴露 gRPC API，按百分比灰度上线，这样可以和单体路径线上对比。

我作为实习生加入后端团队，这个重写就是我的主项目。我向 Tech Lead 汇报，架构决策上和两位资深后端工程师 Pair 工作。

---

## 2. 我做了什么

服务是用 Go 写的，结构上切成三个可组合的阶段。

Candidate Generator 阶段从三个来源拉帖子：用户的关注图谱、一个主题亲和度索引、一组小规模的运营精选。每个来源都是同一个接口的实现，加新来源是改一个文件就完事的事。

Ranker 阶段用一个从 Model Registry 加载出来的模型给候选打分。我把模型接口保持得很小（输入一组候选，输出一组带分的候选），这样数据科学团队换新模型不需要和后端协调发布。我那 12 周里他们通过这条路上了两个新模型。

Post-Processor 阶段做去重、黑名单过滤、多样性策略、最近见过的过滤（用 Redis Sorted Set 实现）。

API 方面我设计了一份 gRPC 契约，里面有三个 RPC：GetFeed、RecordImpression、HealthCheck。有三个客户端服务（移动端 API 网关、推荐测试 Harness、内部 Admin 工具）对接了这个接口。

部署方面，我写了一个 Kubernetes Helm Chart，HPA 同时用 CPU 和 QPS 做依据，用 zap 做结构化 JSON 日志，加上 Prometheus 指标，并且 OpenTelemetry 链路追踪在每个阶段都打通了，这样延迟尖刺出现的时候我们能看出来是哪个阶段拖累的。服务跑在两个区域，前面挂一个区域级 Load Balancer。

正确性和负载方面，我写了单元测试和集成测试，行覆盖率到了 84%，还写了一套 k6 负载测试用例，回放两周的生产流量并放大到 1.5 倍峰值。在任何真实用户流量进来之前，我先跑了两周 Shadow 部署，和单体路径并行运行，然后用一个离线 Diff 任务对比两边返回的 Feed 差异。

---

## 3. 产出

8 周内上到了 25% 灰度。灰度期间测到的产出：

- 两个区域加起来峰值 4,500 QPS。
- 端到端 p99 延迟在 60ms 以内（被替换掉的单体路径在 220ms）。
- A/B 测试中会话时长 +6%，p<0.01 显著。主要驱动力是多样性后处理抓到了单体路径漏掉的重复话题。
- 数据科学团队通过模型接口上了两个新排序模型，没有后端介入。
- Feed 相关故障的 MTTR 减少了大约 40%，归因于每个阶段的链路追踪让定位根因更快。

Tech Lead 让我下一个夏天回去，负责把灰度推到 100%。

## 4. 技术栈

Go、gRPC、Protocol Buffers、Redis、Apache Kafka、PostgreSQL、Kubernetes（用 Helm）、Docker、AWS（EKS、ElastiCache、RDS、ALB）、Prometheus、Grafana、OpenTelemetry、zap（日志）、k6（负载测试）、GitHub Actions。
