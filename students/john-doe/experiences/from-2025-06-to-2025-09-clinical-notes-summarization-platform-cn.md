# 临床病历摘要平台

> 时间：2025-06 到 2025-09。公司：MedSync Health。岗位：软件工程实习生，AI 团队。行业：医疗。

## 1. 背景

MedSync Health 是一家位于波士顿、50 人规模的临床 AI 创业公司。产品要解决的问题是帮初级保健医生少花时间在下班后写病历（行业里普遍的说法是，一位典型的初级保健医生每天要花两到三个小时在下班后补完当天每一位病人的病历文档）。

做法是把原始的 EMR 病历转成结构化的就诊摘要，直接落到病历里。EMR 是 Electronic Medical Record 的缩写，也就是医院用来记录病人数据的电子病历系统，美国市场上 Epic 和 Cerner 是两个最大的厂商。

原始病历是以 FHIR 格式的 JSON 进来的。FHIR 是医疗行业用来交换病历数据的标准格式，可以理解成一种结构化的 JSON Schema，里面给诊断、用药、生命体征等字段都规定好了位置。

后面会提到的 PHI，全称 Protected Health Information，指的是能直接定位到具体病人的信息，比如姓名、生日、地址。美国的 HIPAA 法律要求这类信息在数据离开临床系统之前必须先脱敏。

我入职的时候，团队已经有一个能跑的原型，但是离生产环境差得很远。Prompt（就是我们写给 LLM 这种大语言模型的自然语言指令）很脆。

LLM 偶尔会幻觉出错误的药品剂量，数据摄入 Pipeline 是一个单文件 Python 脚本、偶尔会丢病历。

一个 60 位医生规模的家庭医生集团的 Pilot 八周后就要启动，AI 团队 Lead 让我端到端负责整个重写。最紧张的就是时间。医疗行业的 Pilot 一旦排期就很难推迟，因为客户那边要协调临床、IT 和合规审查一大堆人。

我向 Tech Lead 汇报，紧密配合一位资深后端工程师、一位临床信息学顾问（是一位医生，扮演的是工程团队和真实临床思维之间的翻译角色），以及负责整个 Pilot 业务指标的 Head of Clinical Operations。

## 2. 我做了什么

我重写了系统的三层（摄入、摘要生成、对外服务），而且在这之上我还负责整个数据分析工作，也就是用数据回答"这套东西到底有没有帮到医生"这个问题。

摄入层方面，我把原来的单脚本 Pipeline 换成了事件驱动的架构。AWS Lambda（一种按需运行、不用自己管服务器的小程序）在前面挂着一个 SQS 队列（消息队列，可以理解成一份带缓冲的待办事项列表），消费客户 HL7 网关推送过来的 FHIR Bundle JSON。

每条病历会经过一步 PHI 去标识化（用开源的 Microsoft Presidio，加上临床顾问写的一组正则规则、专门处理 Presidio 漏掉的边缘情况），归一化到我设计的一个 14 表 PostgreSQL Schema 里，同时归档到 S3 做冷存储。这部分本质上就是管道工作，跑稳一周不丢病历之后我就基本不再动它了。

摘要生成层方面，我设计了一套 Prompt 模板，输出格式用 Pydantic 模型做了强约束。Pydantic 是一个 Python 库，让你能把期望的数据形状声明出来，不符合的直接报错。

输出 Schema 涵盖主诉、病史、评估、计划，以及一组引用源段落，这样医生能看到摘要里每一句话是从原始病历的哪一段来的。

我加了一条 Retry 链，第一次响应通不过 Schema 校验时会带着错误信息把 LLM 再问一次。就是这个小技巧把格式不合规率从两位数降到了几乎为零。

为了抓幻觉，我写了一套评估工具，包含八个指标，其中两个（事实覆盖率、引用忠实度）会跑在临床顾问手工标注的一份 300 条病历的 Gold Set 上。

为了让摘要更有依据（行业里叫 grounding，意思是让 LLM 的输出锚定在真实的参考资料上、不再自己编），我搭了一个小的 RAG 层。RAG 全称 Retrieval-Augmented Generation，思路是先把相关的文档检索出来塞进 Prompt，让 LLM 基于这些文档回答、而不是凭它自己的记忆。

我们的语料是公司内部的临床指南。检索器用 OpenAI Embedding 做 k-NN 近邻搜索，向量存在 pgvector 里（pgvector 是一个 PostgreSQL 扩展，让你在普通数据库里就能做向量搜索）。Top 3 的指南条目会作为参考资料注入 Prompt。

对外服务层方面，我用 FastAPI 写了一个服务，对外就一个 summarize 接口，部署在 AWS ECS Fargate 上（这是一种托管容器服务，底层机器由 AWS 帮我们维护），前面挂 Application Load Balancer。我加了 Prometheus 指标、用 structlog 做结构化 JSON 日志、用 OpenTelemetry 做链路追踪，这样每一次请求的耗时花在了哪一步都看得到。

我工作里的另外一半，老实说也是我学到东西最多的一半，就是在这套系统之上做数据分析。一旦系统开始处理真实病历，问题就从"系统能不能跑"变成了"它到底有没有帮到任何一个医生"。这个问题只有数据能回答。

我做的第一件事是在 Tableau 上搭了一个医生采用率仪表盘。Tableau 是工业界最常见的 BI（商业智能）工具，可以理解成一个可视化的 SQL 编辑器，把查询结果直接变成图表和共享仪表盘，非工程师也能看。

这个仪表盘从 PostgreSQL 里拉数据，按 60 位 Pilot 医生逐个展示他们的采用率（医生有多大比例把 AI 摘要接受到了病历里、而不是无视）、平均每个病例节省的时间，以及他们在每周满意度调查里的打分。

等积累了两周数据，分组特征就跳出来了：有重度用户在 80% 以上的病例都用了 AI 摘要，有中度用户在 30% 到 60% 之间，还有怀疑派低于 20%。

临床运营团队就拿这个分组结果做精准回访培训、专门去找那批怀疑派，而不是给所有 60 位医生群发一封通用邮件。Head of Clinical Operations 后来告诉我，第六周满意度能拉起来，靠的就是这种精准触达。

第二件事是对摘要长度做 A/B 测试。早期几位医生抱怨摘要太长，在接诊间隙几秒钟根本扫不完。我们直觉上觉得短一点会更好，但直觉不是证据。

我设计了两个版本的 A/B 测试，长版本大概 250 词，短版本大概 100 词。我把 30 位测试医生用分层随机化（Stratified Randomization）的方法分成两组，所谓分层随机化就是确保两组在专科、年资、患者量这些维度上的比例接近、保证比较是公平的。

我跟了 4 周的接受率（医生有没有把摘要复制进病历、还是直接关掉）。我用 Python 的 scipy.stats 跑了一个卡方检验（chi-squared test，用来比较两组比例差异的标准统计方法）。

短版本的接受率高出 14%，p 值小于 0.05（意思是这个差异由纯随机产生的概率低于 5%）。基于这个结果，团队把短版本推到了全公司。

第三件事是用 SQL 探索不同专科的摘要质量。我在 25 万条病历的语料上写 SQL 查询，找出哪些临床专科的摘要质量分最低。Pediatrics（儿科）、OB/GYN（妇产科）、Behavioral Health（行为健康）三个专科垫底。

我把这个发现拿去找临床顾问，他确认这三个专科的病历结构确实非典型（儿科的生命体征是按年龄相对的，行为健康的病历是大段叙述性的自由文本，OB/GYN 的病历里混入了不像普通就诊记录的产科史），通用 Prompt 处理得不好。

我把 Prompt 迭代的优先级集中在这三个类别上，把它们的周度质量分单独拉了一个视图来跟，到第 7 周三个专科都越过了 75% 的质量阈值。

第四件事把前面这些都串了起来。我做了一份一页纸的周度 KPI 报告，覆盖 PHI 脱敏精确率、摘要质量分、端到端延迟、医生满意度，以及采用率分组分布。CTO 和 Head of Clinical Operations 每周一的 Leadership Meeting 上都会看这份报告。

实习结束的时候，这份报告已经成了"Pilot 推进得怎么样"这个问题的标准答案，取代了之前散在 Slack 各种群里、截图和零散更新拼起来的那种没人完全相信的版本。

## 3. 产出

实习结束的时候，系统已经在那个 60 位医生的 Pilot 站点跑上生产。

- 历史回填阶段处理了 250,000 条临床病历，生产环境每天大概 4,000 条新病历。
- 医生每条病例的查阅时间从基线的 12 分钟降到大约 4 分钟。这个数据是用 EMR 的用户行为埋点测的，统计的是 30 位医生在前后两周的对比。
- Pilot 第六周的医生满意度调查是 91%，相比第二周的 74% 有显著提升，靠的是采用率仪表盘支持的那波精准培训。
- 摘要长度 A/B 测试中，短版本的接受率高出 14%（p 小于 0.05），后续成为默认版本。
- 针对质量最差的三个专科（Pediatrics、OB/GYN、Behavioral Health）做的 Prompt 迭代，把三者在第 7 周都拉过了 75% 的质量阈值。
- 结构化输出格式不合规率从原型阶段的 11% 降到生产阶段的 0.5% 以下，主要靠 Retry 链加 Prompt 里塞例子的组合。
- PHI 去标识化在内部测试集上的精确率是 99.4%，剩下两个假阳性是临床医生在审核时抓到的。
- 周度 KPI 报告成为每周一 Leadership Meeting 的固定材料。
