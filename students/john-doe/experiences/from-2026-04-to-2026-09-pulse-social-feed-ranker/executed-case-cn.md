# Feed 排序微服务

> 时间：2026-06 到 2026-09。公司：Pulse Social。岗位：软件工程实习生，后端团队。行业：消费社交。

## 1. 背景

Pulse Social 是一家 200 人规模的消费社交产品，月活大概 800 万。它的主战场是 Home Feed，也就是你打开 App 第一眼看到的那条不断下滑的帖子流。

这些帖子的顺序不是随机的。有一段程序会把所有可能展示给你的帖子打分、排序，然后把排在前面的几条交还给手机端。这段程序就叫 Feed Ranker（排序器）。它做决策的质量，基本上就是用户口中"这个 App 用着很爽"或者"这个 App 越用越没意思"的来源。

在 Pulse，这个 Feed Ranker 是在一个 Python 单体里慢慢长出来的。所谓单体（Monolith），指的是所有功能都挤在同一份代码里、必须作为一个整体一起发布的大型应用。几年下来，Pulse 的排序逻辑、从数据库拉帖子的逻辑、内容审核的逻辑全都纠缠在一起，里面还埋着几个半死不活的实验代码，没人愿意删，因为也没人记得谁是 Owner。

症状是可以预见的。高峰期延迟尖刺很常见，p99 在 220ms 上下。p99 延迟指的是最慢的那 1% 请求所花的响应时间，工程师最关心这个数字，因为正是这些慢请求会被用户真实感知到、然后跑去投诉。

发布流程同样糟糕。想上一个新的排序模型，往往要花好几天，因为得把整个单体一起重新部署，还要跑一个跟排序毫无关系的、包含上百项检查的测试套件，然后再人工盯着灰度。数据科学团队手头攒了一堆模型想法，但因为这个发布税太高，他们一直没法把这些想法上线。

后端 Tech Lead 想把排序部分从单体里抽出来，做成一个干净的微服务。所谓微服务（Microservice），就是一个独立部署、只做一件事的小型服务，是过去"一个大应用包打天下"那种风格的现代替代方案。

方案本身很直接：用 Go 写，性能可预期、内存占用小；把工作拆成可组合的几个阶段（候选生成、排序、后处理），这样每个阶段都可以独立推理、独立测试；对外暴露 gRPC API；按百分比灰度上线，和单体路径在线上对比，一旦有问题可以瞬间回滚。

我作为实习生加入后端团队，这个重写就是我的主项目。我向 Tech Lead 汇报，架构决策上和两位资深后端工程师 Pair 工作。

这个角色定位很关键。这次重写不是一个边角的实验项目，而是整个团队当季度的主押注，被高层盯着进度，老的单体路径甚至已经定好了一个真实的下线 Deadline。作为一个实习生 Own 这件事的代价是：我拿到了远超这个职级常见水平的信任，也承担了远超这个职级常见水平的责任。

## 2. 我做了什么

服务是用 Go 写的，结构上切成三个可组合的阶段，每一次 Feed 请求都会按顺序走完这三步。

第一步是 Candidate Generator（候选生成）。在给帖子打分排序之前，你得先决定有哪些帖子是有资格被展示给某个用户的，这一步就叫候选生成，"我到底有什么可以展示给这个人"的大部分逻辑都住在这里。

我的实现从三个来源拉候选：用户的关注图谱（这个人关注了谁）、一个主题亲和度索引（这个人过去经常互动的主题）、以及一组小规模的运营精选（内容团队希望加权曝光的条目）。每个来源并行执行，各自最多返回几百条候选，然后合并去重，再交给排序器。

每个来源都是同一个 Go 接口的实现。听起来是个小细节，但实际效果很大。加一个新来源变成了"改一个文件就完事"的事，不需要全团队 Code Review。后来内容团队自己上了一个"你所在城市的热门"来源，只用了一位工程师来 Review。

第二步是 Ranker（排序器）。它从内部的 Model Registry 加载一个模型，用这个模型给每个候选打分。我刻意把模型接口设计得非常小：输入一组候选，输出一组带分的候选。这背后的考虑既有技术原因，也有团队协作原因。我不想让数据科学团队每换一个模型就得和后端协调一次发布。

我那 12 周里他们通过这条路上了两个新模型，全程没有后端介入，这是整个项目里工作流上最大的一个 Win。我简历上对应的那条 Bullet 写的是"重构了模型发布通路，让换模型这件事完全不再碰后端"，听起来比重写本身要轻，但 Mentor 们说团队感觉"被解开了枷锁"，指的就是这条改动。

第三步是 Post-Processor（后处理）。它负责去重、黑名单过滤、多样性策略（避免连续五条都是同一个话题），以及"最近见过"过滤（把用户最近几个小时已经滑过的帖子压下去）。"最近见过"这个过滤用 Redis Sorted Set 实现，可以让我在大约 1 毫秒内完成一次"读取并更新某用户历史"的操作。我们当时实际收集到过一类用户吐槽："我刚刚不是才看过这条吗？"多样性加上"最近见过"正是冲着这类抱怨去做的。

API 方面我设计了一份 gRPC 契约。gRPC 是一种让运行在不同机器上的两个服务通过网络相互调用对方函数的方式。它比大多数网站用的那种比较老的 REST/JSON 风格更快、类型校验更严格，这一点在后端内部要每秒服务几千个请求的时候特别重要。

契约里定义了三个 RPC：GetFeed（用户每次打开或者刷新 Feed 时调用）、RecordImpression（用户滑过每一条帖子时调用，让系统知道用户实际看到了什么）、HealthCheck（由 Load Balancer 调用，用来判断这一份服务实例还活着没）。有三个内部客户端服务对接了这套接口：移动端 API 网关（手机 App 直接对话的那个服务）、数据科学用的推荐测试 Harness、以及一个内部 Admin 工具（内容运营用来排查用户反馈"我为什么会看到这条帖子"的问题）。

部署方面，我写了一个 Kubernetes Helm Chart。Kubernetes 是业界标准的"在很多台机器上自动跑很多份服务副本"的系统。如果有一台机器挂了，Kubernetes 会自动在别的地方再起一份替代，全程不需要人介入。Helm Chart 则是一份打包好的"配方"，告诉 Kubernetes 这个服务到底要怎么跑。

我把 HPA（水平自动扩缩容）同时挂在 CPU 和 QPS 两个指标上，让集群可以随真实流量伸缩，再用 zap 做结构化 JSON 日志，并按业界标准的 Golden Signals（请求速率、错误率、延迟分布、饱和度）导出 Prometheus 指标。

我最在意的部分是 OpenTelemetry 链路追踪在每个阶段都打通。一旦延迟变高，我们打开一个 Dashboard 就能立刻看出来到底是候选生成、模型调用、还是后处理拖累的。在单体里，一次事故往往从"Feed 变慢了"开始，几个小时后才有人 grep 上百万行日志找到根因。有了分阶段的 Trace 之后，同样的诊断只要几分钟。服务跑在两个 AWS 区域，前面挂一个区域级 Load Balancer。

正确性和负载方面，我写了单元测试和集成测试，行覆盖率到了 84%，还写了一套 k6 负载测试用例，回放两周的录制生产流量并放大到 1.5 倍峰值。k6 是一个用代码描述压测流量、然后按你指定的强度往上推的负载测试工具。1.5 倍这个数字不是拍脑袋来的。我们选这个倍数的考虑是：如果新服务在这种压力下扛得住，那意味着我们还为后续一年的自然增长留好了缓冲。

在任何真实用户流量进到新服务之前，我先跑了两周的 Shadow 部署。Shadow 部署的意思是：让新服务和老服务并行跑，把真实的生产流量也发给新服务，但是新服务的响应直接扔掉，给用户的还是老服务的返回。这样可以在不影响用户的前提下，用真实流量去测新服务的延迟、错误率和输出差异。一个离线 Diff 任务会对比两边返回的 Feed，把差异大到值得人工排查的 Case 标出来。

Shadow 第一周就抓到了一个真实 Bug。新排序器对大约 0.2% 的用户返回了空 Feed，这些人后来发现都是全新注册的账号：没有关注、没有主题历史。候选生成没拿到任何东西，排序器没东西可以打分，于是返回了空列表。我给 Candidate Generator 加了一个"运营冷启动"兜底：如果另外两个来源拿到的条目少于某个阈值，就从运营池里补满。这个 Bug 从来没碰到过真实用户。

Shadow 第二周浮出来一个更隐蔽的问题。模型调用偶尔会超过 200ms，原因是候选集对应的特征拉取走了一条慢路径。我加了一个单次请求的预算限制，再加上一个并行化的特征拉取步骤，把长尾压回了正常范围。这两个问题在带合成数据的 Staging 环境里都抓不到，必须靠真实生产流量的形状才会暴露出来，这正是 Shadow 部署的价值。

Shadow 之后是一个谨慎的百分比灰度：1%、5%、25%。每一档我们都会先压平一段时间，盯几天 Dashboard，确认延迟、错误率和业务指标都干净了，才推下一档。我和 Tech Lead 一开始就说好：无论指标看起来多漂亮，都不在同一天连推两档，因为最严重的事故往往是在变更后一两天、流量结构变化之后才浮出来。

## 3. 产出

服务在 8 周内上到了 25% 灰度。灰度期间测到的产出：

服务在两个区域加起来峰值跑到了 4,500 QPS（每秒请求数）。说人话就是，在一天中最忙的那个时段，每秒大约有 4,500 个用户来加载 Feed，自动扩缩容也没有撑爆。

作为对比，被替换掉的单体路径在同样的流量下已经接近自身扩容上限。新服务还有大约 50% 的余量，HPA 才需要再调一次。

端到端 p99 延迟稳定在 60ms 以内，被替换掉的单体路径是 220ms。也就是说对最慢的那 1% 请求（用户真正能感觉到卡顿的那部分），新路径几乎快了四倍。

A/B 测试中会话时长 +6%，p<0.01 显著。Feed 上的 A/B 测试是这么做的：一半用户用新排序器，一半用户继续用老的，然后看新排序器那一组用户平均花在 App 里的时间是不是更多。

+6% 的意思是新排序器组用户每次会话平均多停留了 6%，而 p<0.01 的意思是这个结果纯属巧合的概率非常低（少于 1% 的概率是随机抽样抽出来的假阳性）。主要驱动力是多样性后处理抓到了单体路径漏掉的重复话题。在公司内部，Home Feed 的会话时长 +6% 是一个一年多没人动过的数字，最后成了整个项目对外汇报时的头号指标。

数据科学团队通过模型接口上了两个新排序模型，没有后端介入，这也验证了当初"把模型接口做到最小"那个设计决策是对的。

重写之前换一次模型要后端工程师花差不多一周时间做对接，重写之后数据科学团队自己几小时就能搞定。光是这一条改变，就改写了整个公司在 Feed 质量上做实验的节奏。

Feed 相关故障的 MTTR（平均恢复时间）减少了大约 40%，团队归因于每个阶段的链路追踪让定位根因比在单体里快得多。这段恢复时间越短，故障期间看到劣化 Feed 的用户就越少，这个数字直接换算成更少的客服工单。

Tech Lead 让我下一个夏天回去，负责把灰度从 25% 推到 100%。除了灰度本身，下一个夏天的计划是按同样的"分阶段管道"模板把单体里的另外两块也拆出来，让这次重写最终沉淀成其他工程师可以照搬的一个模式，而不仅仅是一次一次性的工程。

## 4. 技术栈

Go、gRPC、Protocol Buffers、Redis、Apache Kafka、PostgreSQL、Kubernetes（用 Helm）、Docker、AWS（EKS、ElastiCache、RDS、ALB）、Prometheus、Grafana、OpenTelemetry、zap（日志）、k6（负载测试）、GitHub Actions。
