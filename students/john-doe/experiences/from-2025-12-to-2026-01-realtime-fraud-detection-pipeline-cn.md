# 实时欺诈检测 Pipeline

> 时间：2025-12 到 2026-01。公司：Forge Trading。岗位：数据分析与 ML 合同工。行业：金融服务。

## 1. 背景

Forge Trading 是一家中等规模的衍生品经纪商。（衍生品经纪商是一类金融公司，帮客户买卖那种价格挂钩在别的东西上的合约，比如挂钩股票或者商品价格。因为这类业务里资金流动又快又大，所以欺诈检测是一件长年要紧盯的事。）

Compliance 团队（合规团队，公司内部专门负责保证交易合规、防止公司被用来洗钱或诈骗的部门）当时跑的是一套老的规则引擎做交易欺诈检测。这套规则引擎是 80 条左右手写的 if-else 规则，过去几年里不同工程师和分析师陆陆续续堆出来的。

每天这套引擎会标记掉约 0.8% 的交易交给人工复核。问题在于，被标记的交易里约 78% 是假阳性。（规则引擎看着可疑，但人工复核后判定其实没问题。）Compliance 的分析师大量时间花在排查正常交易上。

团队想试一套 ML 系统来辅助、而不是替代规则引擎。（机器学习模型从历史数据里学欺诈的规律，而不是靠人手写规则。希望就是模型能抓到一样多的真欺诈，同时少误报很多。）

Head of Data 找我做一个为期六周的寒假合同项目，让我牵头数据分析和建模这一块。同时项目里还有两位资深数据工程师（负责底层流式基础设施）和一位量化分析师（数学和统计学背景，专门设计交易信号和风险模型的角色）一起配合。

项目范围一开始就划得很窄。先弄清楚为什么规则引擎一直在乱报警。再训出一个 baseline 的 ML 模型。然后用 Shadow 模式（让新模型和老的规则引擎并行跑、但暂时不让它真正影响业务决策的一种灰度方式）评估。最后出一份是否值得继续投入的书面建议。

## 2. 我做了什么

我刚进项目的时候，团队里没人能讲清楚为什么这套老规则引擎一直在错报。大家都有自己的猜测，但没人真正坐下来翻过数据。

我做的第一件事，就是把六个月的 Compliance 标记历史拉进了 Snowflake。（Snowflake 是一个云端数据仓库，本质上就是一个为分析场景设计的超大 SQL 数据库，和处理在线交易的那种数据库不是一类东西。）

然后我写了一组 SQL，把标记按商户类目、地理位置、时间段、以及最后人工复核的处置结果做分组分析。几天之内，图景就慢慢清晰起来了。

结果非常清晰。分析师大约 80% 的复核工时其实只花在三类情形上。

第一类是周末出现的跨境旅行交易。第二类是节假日零售消费的峰值。第三类是一小撮商户，他们的类目代码在上游被第三方数据源错误分类了。

我把这套分析写成了一页纸的备忘录给 Head of Compliance，配上每一类的图表，并附上了一份建议下线的规则清单。这份 memo 后来成了整个团队对问题的共同认知，也定下了后面工作的方向。

差不多同一时间，我注意到 Compliance 团队的决策依据其实是一份每周的 Excel 表。那份表由一位内部分析师花将近两天时间手工拼出来。等送到他们邮箱的时候，数据已经滞后好几天了。我提议用一个实时 Dashboard 取代它。

我用 Looker 把这个 Dashboard 搭了起来。（Looker 是一类业务智能 BI 工具，性质上类似 Tableau，让不会写代码的同事可以靠点点点和筛选条件去探索数据，而不用写 SQL。）这个 Dashboard 追踪每日标记数量、假阳性率、分析师复核耗时，并按我那份 memo 里识别出的三大类做拆分展示，每小时自动刷新一次。

到我项目结束的时候，Compliance 团队每天早会都开着这个 Dashboard 看，那份慢吞吞的 Excel 周报也悄悄退役了。

流式 Pipeline 这一侧主要由两位资深数据工程师负责。这里简单交代一下背景：Forge 内部订单管理系统的每一笔交易事件，通过 Apache Kafka 经 AWS MSK 写入 Snowflake 一张表，峰值流量大约 12,000 事件每秒。（Kafka 是一种高吞吐量的消息中间件，专门用来在不同系统之间实时搬运事件。）

再由一个 Spark Structured Streaming 任务把每条事件和六个滚动特征聚合（1、5、30 分钟的交易频次，平均名义金额，地理异常分，商户风险分）做 Join，然后用一个 ML 模型打分。我自己负责的是建立在这条流上的分析层和建模层。

模型这一块，我和量化分析师一起从交易历史里整理出大约 30 个特征。有些特征比较直接，就是计数、求平均。另一些就更细一点，比如地理异常分，用来衡量一笔交易的发生地点偏离客户日常活动范围有多远。

我用六个月的标注历史交易（约 400 万条）训了一个 XGBoost 模型。（XGBoost 是一种很常用的机器学习算法，特别擅长处理表格化的业务数据。在判断一笔交易是不是欺诈、一个客户会不会流失、一笔贷款会不会违约这类问题里几乎是默认首选。）

调参用 Optuna 做了贝叶斯搜索。（Optuna 是一个会智能地搜索最优参数组合的库，不需要傻乎乎地把所有组合都试一遍。）最终模型在 Holdout（留出验证的那一个月）数据上 AUC 是 0.94。（AUC 是一个介于 0 到 1 之间的指标，衡量模型区分两类样本的能力。0.5 是瞎猜，1.0 是完美。）

在 Head of Compliance 同意切换到实际打分之前，她要求做一次严谨的事前事后对比。我设计了一个回溯研究来回答她的问题。（回溯研究是一种把新旧两套系统在历史数据上重新跑一遍、再对比结果的分析方式，过程中要控制时间段、商户结构这些干扰因素。）

我把 ML 模型和老规则引擎都在同一份 400 万条历史交易上跑了一遍。然后用 Python 算出了假阳性下降幅度的 95% 置信区间。（用 statsmodels 做置信区间，pandas 和 scipy 做数据处理。）

我把结果画成了一张带误差棒的成对柱状图，让非技术背景的高管也能一眼看明白对比结果。

我把这份研究汇报给了执行评审委员会。最终那个 35% 的假阳性下降幅度（而且置信区间很窄）就是委员会拍板批准把模型转成实际打分的主要依据。

为了在模型上线后监控漂移，我给 Top 10 特征接入了 PSI 跟踪。（PSI 全称 population stability index，是一种统计指标，衡量某个特征在线上数据里的分布相比训练时偏离了多远。PSI 升高就是在提醒你：模型现在看到的世界，可能已经不是它训练时见过的那个世界了。）

Shadow 期间一共触发了三次告警。其中两次分析师确认是上游真实的协变量漂移。

我们提前重训，没有等模型在生产里真正掉性能，这正是当初接入 PSI 跟踪想要达到的效果。

最后一块分析工作是为 Compliance 的分析师本人做的。这些人是手动复核被标记交易的同事，对业务的理解非常深，但不会写代码。我想给他们做一个既尊重他们判断、又能给他们提供更锐利信号的工具。

我给他们写了一组 SQL 探索式 Notebook。（Notebook 可以理解成一个数字版的实验记录本，可以把查询、图表和文字解释混在同一个文档里。）这些 Notebook 揭示出在历史数据里，哪些交易模式更可能对应已确认的欺诈，哪些更可能对应已确认的正常交易。

其中有一个发现特别引起他们注意。当地理异常分超过某个阈值、同时商户风险分也超过另一个阈值时，这种组合是真欺诈的概率是单看任一项信号时的 12 倍。Compliance 团队把这些发现写进了他们的人工复核手册，让分析师知道在排查时应该优先看哪些信号组合。

## 3. 产出

系统在生产交易流上 Shadow 跑了两周。最终给 Head of Compliance 的报告里，分析和建模两方面的产出都有覆盖。

分析这一侧，那份假阳性模式 memo 给团队提供了一份很具体的待下线规则清单，对应了约 80% 被浪费的人工复核工时。

Looker Dashboard 在四周内成了 Compliance 团队每日早会的固定参考工具，旧的 Excel 周报顺利退役。

回溯研究上到了执行评审委员会，是他们最终拍板把模型切到实际打分的关键依据。基于 SQL 探索 Notebook 的分析师手册更新，也让人工复核的同事拿到了一个明确的信号组合优先级。

模型和 Pipeline 这一侧，系统峰值处理 12,000 events/s，老 Pipeline 最高大概 5,000。Holdout 上 AUC 0.94。在选定工作点上，召回率与规则引擎持平，也就是 Shadow 期间没有漏掉欺诈，而假阳性标记率下降了 35%。

两周 Shadow 窗口里抓到了 120 万美元规则引擎漏掉的真实欺诈交易。我离开之后不久，团队正式批准把这套系统转成实际打分。

## 4. 技术栈

Python（pandas、scipy、statsmodels、scikit-learn）、SQL、XGBoost、Optuna、Snowflake、Looker、Jupyter、Apache Kafka（AWS MSK）、Apache Spark Structured Streaming、dbt、Redis、Apache Airflow、Great Expectations、AWS（MSK、EKS、S3、IAM）、Docker、Prometheus、Grafana。
