# 05 — Interview playbook for `learn_build_resume_matrix`

This playbook is the **reference** the `learn-this-project-interview` skill grades against. Model answers below are for the skill's internal use — they must **never** be shown to the candidate during an interview round. Surface specific gaps in the debrief instead.

## The 90-second pitch — model script

> I built a **methodology and skill library for the US job-search workflow**, focused on producing one defensible master resume from which any number of targeted resumes can be derived by deletion only. The project has two interlocking pieces: a **13-lesson curriculum** that teaches the conceptual model, and a **fleet of 10 agent skills** that operationalize each stage of the workflow — gap analysis between a student's current state and a target JD, deliberate case design with a separate-context reviewer, execution planning with per-gap POCs and tutorial scaffolds, concept-by-concept coaching, and a clean-context mock interview. The architectural centerpieces are the **1+N resume matrix** (one master holds all variants; derived resumes are deletion only), the **writer/reviewer pairing pattern** (every major artifact has an authoring skill plus a critical-reviewer skill), and the **file-based design-review loop** between mini-project-design and mini-project-review which lets long iteration rounds survive crashes and tool switches. There's one fictional worked example — John Doe with three projects across healthcare, finance, and consumer-backend — demonstrating the full pipeline end-to-end. The deliberate gaps right now are: no test suite, no outcome instrumentation (callback / interview / offer logging), and validation evidence rests on one synthetic case study.

## Round 1 — What you have (mechanism, data flow, architecture)

### R1-Q1 — Walk me through what happens when a user invokes `/qualify-gap-analyze`

- **Model answer.** The user invokes from inside a `students/<name>/experiences/<exp>/qualify-for-<company>-<role>/` folder. The skill reads three things: the master resume path, the target JD, and (optionally) the landscape research docs. It produces one file — `gap-analysis-cn.md` — with a relevance check, a severity-classified breakdown table (🔴 Core / 🟡 Important / 🟠 Nice-to-have), per-gap deep dives quoting the JD verbatim alongside what the current resume shows, cross-gap entanglement notes (which gaps depend on which), a verdict, and handoff notes for the next two skills. The skill is deliberately one-purpose: it diagnoses but does not prescribe a fill plan — `qualify-execution-plan` does that, downstream.
- **Follow-ups the interviewer might press with.** Why split diagnosis from prescription? What stops the gap-analyze step from being warped by what's easy to fix? How does the skill know which experience folder the user is in?
- **What a weak answer sounds like.** "It compares the resume to the JD and tells you what's missing." (No file paths, no severity scale, no awareness of the diagnosis-vs-prescription split.)

### R1-Q2 — Walk me through the 6-stage qualify pipeline. What does each stage take in and produce out?

- **Model answer.** Stage 1 — `understand-landscape` (prerequisite, not in this repo): produces 5 docs in `landscape/` (industry / company / role / market / index). Stage 2 — `qualify-gap-analyze`: reads resume + JD + optional landscape; produces `gap-analysis-cn.md`. Stage 3 — `mini-project-design` + `mini-project-review` loop: reads gap + JD + thin case (elevate) OR JD + execution venue (from-scratch); produces `case-cn.md` and `review-NN.md` / `fix-NN.md` until verdict = approve. Stage 4 — `qualify-execution-plan`: reads gap + approved case + JD; produces `execution-plan-cn.md`, `pocs/poc-NN-<slug>/README-cn.md` per gap, and `tutorials/NN-<slug>-cn.md` stubs. Stage 5 — `qualify-coach`: reads execution plan + POCs + optional case/gap; produces `coach-notes/concept-<slug>.md` per acknowledged concept plus `coach-notes/_progress-cn.md`. Stage 6 — `qualify-mock-interview` (separate conversation context!): reads JD + case + execution-plan + coach-notes; produces `mock-interview-{round}.md` with transcript + debrief. **Inputs stack across stages** — each later stage gets everything the earlier stages produced, which is where depth compounds.
- **Follow-ups.** Where does the data physically live? Why six stages and not three or twelve? Could you skip stages?
- **What a weak answer sounds like.** Listing the six stages by name without mentioning what each consumes and produces, or omitting the input-stacking property.

### R1-Q3 — Talk me through your master resume schema. What's in `resume.md`?

- **Model answer.** One master holds: contact + identity header; **Summary section** with multiple Variants (Variant A, B, C…) — one per Job Family direction (AI Engineer, Data Analyst, Software Engineer, etc.); **Experience section** with one entry per real work experience and **multiple Bullet Sets** per entry (Bullet Set 1, 2, … each tagged with a Job Family angle like "AI emphasis" or "Data Analytics emphasis"); **Skills section** as a single union of every tech mentioned anywhere; **Education**, **Projects**, etc. Every Summary Variant and (usually) every Bullet Set carries an inline `> **Rationale**` blockquote explaining verb / noun / Identity choices so future edits stay coherent. Derived resumes (`resume-role-1.md` etc.) are produced by **deletion only** from the master.
- **Follow-ups.** Why deletion-only? How do you handle a Bullet Set that becomes stale? How do you keep N Summary Variants from contradicting each other?
- **What a weak answer sounds like.** "It's a resume with multiple versions" — no awareness of the Variants-as-first-class-objects structure or the rationale blockquotes.

### R1-Q4 — How do `mini-project-design` and `mini-project-review` communicate?

- **Model answer.** Exclusively through disk files. Design writes `case-cn.md`; review reads it and writes `review-NN.md`; design reads the review and writes `fix-NN.md` plus revisions to `case-cn.md`. They run in **separate Claude Code conversations** (typically separate terminals). They do not share conversation context. This buys four things: (1) crash-robustness — state is on disk; either terminal can be killed and resumed; (2) auditability — every round is a permanent artifact; (3) tool-agnostic — either skill could be swapped to a different model or a human reviewer; (4) iteration speed — long loops can span days without conversation-context bloat. The reviewer is also read-only on the case and fix files — it can only write `review-NN.md`.
- **Follow-ups.** Why read-only? What stops the reviewer from quietly co-authoring? How does the NN auto-increment?
- **What a weak answer sounds like.** "They pass files back and forth" — no awareness of the read-only constraint or the separate-context discipline.

### R1-Q5 — The bullet-writer enforces a B1→B4 progression. Walk me through it.

- **Model answer.** B1 — HR-readable picture: one sentence that a non-technical reader gets in 5 seconds. B2 — key technical decision: the single most important architectural choice and one-sentence defense of it. B3 — hardest sub-problem: where engineering judgment lived; the part the candidate would talk about for 10 minutes if asked. B4 — ownership and cross-team impact: who depended on this work, what cross-team coordination it required, what stakeholder outcome it produced. The count flexes 2–5 depending on what the case actually supports. Padding to 4 when the case doesn't have a B3 produces an indefensible bullet — collapses at the first follow-up. Each bullet is separately defensible: an interviewer can pick any one and probe 2–3 layers deep.
- **Follow-ups.** What does "the case supports it" actually mean — what's the evidence threshold? Can you give me a case where the right count would be 2 instead of 4?
- **What a weak answer sounds like.** Reciting B1–B4 without the "each bullet must be separately defensible" principle, or without the count-flex rule.

### R1-Q6 — Where does the master resume live and why?

- **Model answer.** On GitHub, in markdown (`resume.md` or `<name>/resume.md`). Three reasons: version control (every edit recoverable; the master grows over years), branching (try restructures on a branch), externalized backup (no laptop-failure risk). Google Docs is layered on top for **layout + mentor collaboration** (in-line comments). PDF is the **submission artifact** the recruiter receives. The three-stage flow (GitHub → Docs → PDF) decouples authoring from layout from submission. Notion isn't text-diffable; Docs has revision history but isn't grep-able; a single laptop file has no backup.
- **Follow-ups.** What happens when mentor edits in Google Docs — how do those flow back to GitHub? What stops the master and the Docs version from diverging?
- **What a weak answer sounds like.** "On GitHub" — no awareness of the three-stage flow or why each tool has its role.

## Round 2 — What you'd elevate (with 3–6 more months)

### R2-Q1 — If you had three more months on this project, what would you build first and why?

- **Model answer.** A small `tests/` suite — `test_skill_frontmatter.py`, `test_curriculum_link_integrity.py`, `test_john_doe_artifact_completeness.py`, `test_chinese_english_parity.py` — plus GitHub Actions running them on every PR. The reason it's first: the project is 100% prose + skill definitions with no mechanical safety, and every artifact cross-references every other one (the curriculum cites skill names, the skills cite lesson numbers, the worked example cites both). Drift today is invisible. The tests are cheap (~1–2 days), parametrize over globs, and immediately make the next 3 months of work safer. Without tests, the second priority — adding 2–3 more worked examples — would itself drift the curriculum.
- **Follow-ups.** Why this before adding more worked examples? Aren't tests harder to write than they look here? What happens when the test suite gets out of sync with the actual structure?
- **What a weak answer sounds like.** "Write more lessons" — no acknowledgment that the bottleneck is validation, not curriculum volume.

### R2-Q2 — What's the highest-leverage non-test investment you'd make?

- **Model answer.** Outcome instrumentation: a structured `students/<name>/applications.jsonl` log capturing per-application outcomes (submitted / callback / on-site / offer / rejection-reason / time-to-response). Today the curriculum ends at "submit" — there's no closed loop. With outcome data, the methodology starts producing hit-rate evidence: which Bullet Sets get callbacks vs which don't; which Summary Variants land for which Job Families; which gaps surfaced in actual interviews vs which were never asked about. That feedback feeds back to the next `mini-project-design` cycle. Without it, the methodology is unfalsifiable.
- **Follow-ups.** How would you handle privacy / consent for real data? Would a JSONL grow unwieldy? What's the right grain — per application or per round?
- **What a weak answer sounds like.** "Build a dashboard" — leads with tooling instead of leading with the data shape.

### R2-Q3 — How would you address the "one fictional student" credibility gap?

- **Model answer.** Add 2–4 more worked examples: a career-changer (e.g., teacher → data analyst — different gap-analysis shape), a returning-from-leave candidate (handles resume gaps), an international student (visa-status constraints surfaced by gap-analyze), and at least one **real** anonymized case where the methodology was applied and the outcome is documented. The fictional John Doe demonstrates *what* the artifacts look like; what's missing is evidence that *the methodology generalizes* across starting positions. The real-anonymized case is the highest-leverage of the four because outside readers will reasonably suspect cherry-picking even with multiple synthetic students.
- **Follow-ups.** How do you anonymize a resume + project documents without losing what makes them concrete? What if the real candidate's outcome was a rejection — do you still publish it?
- **What a weak answer sounds like.** "Add more synthetic examples" — doesn't address the credibility gap, just adds more of the same.

### R2-Q4 — The qualify-coach and qualify-mock-interview must run in separate conversations. Is there a way to make that less error-prone?

- **Model answer.** The current state is "documentation + skill-time check" — both SKILL.md files warn the user, and the skill checks at invocation start. A `/qualify-next` orchestration helper (proposed in `03-elevation-roadmap.md` § G) would track pipeline state per qualify-for folder and refuse to invoke mock-interview in the same conversation as coach, or warn loudly. The reason not to *force* it via tooling is that the user should remain the orchestrator — over-automation collapses the methodology's user-in-driver-seat property. A warning + structural assistance is the right answer; a hard automation lock is overreach.
- **Follow-ups.** What does "track pipeline state" actually look like in implementation? Would you need a state file? What invalidates the state?
- **What a weak answer sounds like.** "Automate the whole pipeline" — defeats the user-judgment property of the design.

## Round 3 — Alternatives considered ("why not X?")

### R3-Q1 — Why not collapse `qualify-gap-analyze` and `qualify-execution-plan` into one skill?

- **Model answer.** Splitting them prevents the diagnosis from being warped by what's easy to fix. If one skill produced both the diagnosis and the prescription, it would unconsciously omit gaps it has no good POC for — the diagnosis would degrade to "what we can fix" instead of "what the JD requires". The split forces diagnosis to be honest first and the plan to be ambitious second. Tradeoff: users have to invoke two skills instead of one (slight friction), and the gap-analysis output has to be passed downstream (filesystem dependency). Both are acceptable costs.
- **Follow-ups.** Couldn't a combined skill be prompt-engineered to not skew? What if the user wants the combined skill anyway?
- **Tradeoff to highlight.** Honesty vs ergonomics. Diagnosis fidelity wins.

### R3-Q2 — Why not auto-generate the derived resumes (`resume-role-N.md`) from the master?

- **Model answer.** Tempting, and possible — but the methodology explicitly insists derived resumes come from **deletion only**, performed deliberately by the candidate. Three reasons to keep it manual: (1) the candidate has to *know* which Bullet Sets and which Summary Variant belong in this specific company's resume — that decision is itself part of the application-specific judgment, not a mechanical filter; (2) automating it would invite addition over time (add a custom paragraph for this company, then for that one) — the discipline that prevents the master from forking depends on the friction of manual derivation; (3) lesson 11's GitHub → Docs → PDF flow assumes the derived markdown is a working artifact, edited live during the application-prep session — auto-generation makes that session feel like a build step.
- **Follow-ups.** Couldn't the manual step be a 30-second confirmation rather than a full deletion pass? Where does the line between automation-helpful and automation-harmful live here?
- **Tradeoff to highlight.** Friction is a feature, not a bug, when it preserves discipline.

### R3-Q3 — Why use markdown for the master rather than a structured format like JSON / YAML?

- **Model answer.** Markdown serves three audiences simultaneously: the human (reads it cold), the LLM-driven skills (parse it well enough), and the mentor in Google Docs (paste-friendly). A structured format would make some skill operations cleaner (e.g., consistency checks) but would lose human readability and require a render step before review. Tradeoff: skills like `bullet-reviewer` have to do soft parsing instead of structural traversal, and edge cases (a bullet that includes a `### subhead` accidentally) can confuse the writer. The cost is acceptable for a methodology where the human's judgment is in the loop on every artifact.
- **Follow-ups.** What would you do if you wanted to add real consistency checking — would you maintain a parallel YAML index? Could you go full structured later?
- **Tradeoff to highlight.** Human-first format vs machine-first format. The methodology bets on the human staying central.

### R3-Q4 — Why a writer/reviewer pair instead of a single skill with built-in review?

- **Model answer.** A single skill that "writes and reviews" inherits the writer's framing and can't actually attack its own output. Splitting them lets the reviewer carry a **different prompt and different framing** ("hostile hiring manager", "critical mentor") that operates against the writer's output as adversarial input. It also lets the reviewer be invoked **on demand for high-stakes targets only** — most Bullet Sets stay general-purpose and don't need a review pass. A single skill would either always review (wasted) or never review (no critical pass).
- **Follow-ups.** Couldn't you prompt-engineer one skill to do both well? What's the actual evidence the split improves outputs?
- **Tradeoff to highlight.** Modular sharpness vs ergonomic single-call.

### R3-Q5 — Why not version-pin Claude Code or the specific model in each SKILL.md?

- **Model answer.** Pinning would make the skill fragile against Claude Code updates that change tool semantics, and would make every skill mismatch with the user's actual Claude Code version. The skills are written against the **interface contract** (frontmatter keys, allowed-tools syntax, dialogue patterns) — that contract is stable across model versions. The downside is occasional brittleness when Claude Code adds a new feature the skills don't yet exploit; the upside is the skills keep working as Claude improves. The lesson-smith-* skills (curriculum maintenance) are more sensitive to model output style and could plausibly need pinning later.
- **Follow-ups.** What happens if Anthropic changes the frontmatter spec? How do you keep skills calibrated to a model that's much smarter than the one they were written for?
- **Tradeoff to highlight.** Long-term forward compatibility vs short-term polish.

## Round 4 — Problems hit / debugging hypotheticals

### R4-Q1 — A student runs `qualify-mock-interview` and it's surprisingly soft on them. Walk me through what you'd check.

- **Model answer.** Most likely cause: the student ran mock-interview in the same Claude Code conversation as `qualify-coach`. The coach has memory of where the student struggled and the mock-interview inherits sympathetic framing. Diagnosis steps: ask the student to scroll up — is the coach session above the mock-interview? If yes, kill the terminal, open a fresh one, re-invoke mock-interview from scratch. Second possibility: the JD passed to mock-interview is weaker or vaguer than what the case is sized for — the interviewer scales pushback to JD bar. Third (less likely): the model that day is being unusually generous; re-run with the same fresh-context setup but ask the skill to explicitly probe `harder`.
- **Follow-ups.** What if the student insists they used a fresh terminal? How would you verify? What logs would help?
- **What a weak answer sounds like.** "Tell them to try harder questions" — doesn't diagnose root cause.

### R4-Q2 — The mini-project-design ↔ mini-project-review loop has gone five rounds with no convergence — the verdict keeps coming back `redesign`. What's wrong?

- **Model answer.** Three likely roots: (1) the **case is fundamentally over-scoped** for the student's actual experience — every redesign trims more depth and the reviewer correctly keeps flagging shallowness; intervention is to bring the case down to a smaller scope where the student has real evidence; (2) the **reviewer and designer are talking past each other** — fix-NN.md addresses the wrong items from review-NN.md; intervention is to read the latest review carefully and cross-reference each item to the case before the next fix; (3) **the JD is itself contradictory** (e.g., wants "5 years of X" from a new-grad role) — the gap-analyze step should have flagged this with a relevance verdict before stage 3; if not, regenerate gap-analyze with extra scrutiny.
- **Follow-ups.** When do you give up and switch from elevate-mode to from-scratch? What does it look like when the student is the problem rather than the case?
- **What a weak answer sounds like.** "Keep iterating" — no diagnostic stance.

### R4-Q3 — A user reports that the `bullet-writer` produced a Bullet Set with all bullets starting with "Architected" — but the student is a new grad. What went wrong?

- **Model answer.** The verb-register rule was not enforced for this invocation. Either (a) the student didn't supply their experience level when the skill asked, and `bullet-writer` defaulted to a senior register; (b) the case document itself uses senior-register verbs (claiming "architected a multi-region system" as a class project) and the skill mirrored the case rather than overriding; (c) a regression in the skill's verb-pool logic. Diagnose: check what experience-level argument was passed, read the case to see what verbs *it* used, and look at the `bullet-writer` SKILL.md verb-register section to confirm the rule still encodes new-grad / mid / senior pools. Fix: re-invoke with explicit `--experience new-grad`, or downgrade the case's verb register first.
- **Follow-ups.** Should the writer override an over-claiming case, or should the case be fixed first? Whose responsibility is it to keep registers aligned?
- **What a weak answer sounds like.** "It's a prompt bug" — doesn't separate "user input wrong" from "skill behavior wrong".

### R4-Q4 — A student says they ran `qualify-gap-analyze` and got a single 🔴 Core gap that's exactly what their resume already covers — they think the skill is wrong. How do you debug?

- **Model answer.** First check: did the skill get the right inputs? Sometimes the wrong resume file gets passed (an old draft) or the JD text was paraphrased instead of pasted. Re-run with verified inputs. Second: read the skill's deep-dive section for that gap — gap-analyze quotes the JD verbatim alongside what the resume shows. If the JD quote is genuinely covered by an existing bullet, the skill is wrong and you should report it (and possibly file an issue in the references/). If the JD quote is for a *deeper depth* than the resume shows (e.g., JD wants "production RAG eval", resume shows "ran a RAG demo"), the skill is right — the student is over-counting their evidence. Most cases land in the second bucket, because the methodology's whole point is calibration against the student's own optimism.
- **Follow-ups.** What happens when the skill is actually wrong — how do you fix it without breaking the calibration for other students?
- **What a weak answer sounds like.** "The student is right, the skill is broken" — defaults to the easier explanation.

## Round 5 — Production pushbacks (senior-level pressure)

### R5-Q1 — Suppose this methodology becomes popular and 10,000 students per month run the pipeline. What breaks first?

- **Model answer.** Two things in order. First: the **mentor bottleneck** — lesson 11 assumes a human mentor is available for the Docs collaboration stage; that doesn't scale. The fix is either an AI-driven mentor-reviewer step (essentially extending `bullet-reviewer` and `summary-reviewer` to operate as Docs-comment-style markup), or breaking the mentor expectation explicitly and letting the methodology be "self-driven, optionally mentored". Second: **the verb register and ATS rules drift** — as ATS systems evolve and as recruiter conventions shift, the static rules in `bullet-writer` / `summary-writer` go stale. The fix is putting those rules behind a versioned `references/` doc and having an annual review cycle. Both are foreseeable problems; neither is a near-term blocker.
- **Follow-ups.** What's the failure mode for an outdated verb-register rule — does a wrong bullet actually get someone rejected? How would you measure the methodology's freshness?
- **What a weak answer sounds like.** "Scale the agent skills" — doesn't identify the human-in-the-loop bottleneck.

### R5-Q2 — A privacy regulator asks: where does the student's resume, JD, case, and interview transcript actually go? Walk me through the data flow.

- **Model answer.** Everything stays on the user's local machine in `students/<name>/` plus the Claude Code conversation history (which goes to Anthropic per Claude Code's data policy at invocation time). There is **no project-managed cloud storage**. The user pushes the master resume to *their own* GitHub (a deliberate choice; not the project's GitHub). Google Docs and PDF are also user-managed. The only third-party touch is the LLM API call. For a student concerned about data: (a) use Claude Code's available privacy controls, (b) don't commit `students/<name>/` to a public GitHub if it contains real PII (john-doe is fictional and lives in the public repo deliberately — a placeholder for what a student's folder should look like), (c) consider running the local-mode-friendly skills offline once that's available.
- **Follow-ups.** What about EU students under GDPR? What's the "right to be forgotten" story when transcripts live in Anthropic's logs?
- **What a weak answer sounds like.** "It's all local" — true but glosses the LLM API call.

### R5-Q3 — Suppose a target JD specifies "must be a US citizen". The methodology has the student running gap-analyze, which surfaces it as 🔴 Core. But there's no project, POC, or coaching that can close that gap. What should the methodology do?

- **Model answer.** The gap-analyze skill's **relevance verdict** is supposed to fire here — citizenship / visa / clearance gaps are *unclosable by case design*. The right output is "verdict: not a fit; do not proceed to mini-project-design". The methodology explicitly has the verdict as a stage-2 short-circuit precisely to prevent students from spending 3 months designing a case for a role they can't legally take. If the gap-analyze output flags the citizenship requirement but the student wants to proceed anyway (e.g., they're applying speculatively, or the JD is overstating), the case design happens but the cover-letter / outreach has to address the gap directly. This is one of the rare cases where the methodology says "don't apply" — most gaps are closable; this one isn't.
- **Follow-ups.** What about other "hard gates" — security clearance, specific certifications, time-zone constraints? Do they all use the same verdict path?
- **What a weak answer sounds like.** "The student should still apply" — ignores the diagnostic point of the verdict.

### R5-Q4 — Imagine the bullet-writer suddenly starts producing bullets that look templated — every bullet in every Bullet Set across many students starts with "Built a scalable…". What's the response?

- **Model answer.** First check: is it a regression in the SKILL.md or the references? Read the skill's verb pool and check it hasn't degraded to a single phrase. Second check: is the **case** itself the source — many cases share the word "scalable" and the writer is mirroring? Pull a sample of 5 cases that produced "Built a scalable…" and see if their case docs all said it. Third check: model drift — the underlying model may have a stronger prior toward "scalable" after a version bump; this would show up as the same regression across other skills that produce phrasing (`summary-writer`). The fix is variance enforcement in the writer's prompt ("vary the verb across bullets; never repeat the same verb within a Bullet Set") and a test that asserts a Bullet Set's bullets don't all share a leading verb.
- **Follow-ups.** How would you build the variance test? What's the false-positive rate likely to be — could legitimately-varied bullets accidentally all start with "Built" in valid cases?
- **What a weak answer sounds like.** "Fix the prompt" — no diagnostic decomposition.

### R5-Q5 — A senior reviewer says: "I disagree with the writer/reviewer pairing. You're paying for two LLM calls when one well-prompted call could do both. Convince me."

- **Model answer.** Three points. (1) The writer and reviewer carry **different framings** — the writer is constructive (helping the student articulate); the reviewer is adversarial (playing critical hiring manager). A single skill collapses to the writer's framing because the writer's output anchors the model. (2) The reviewer is **invoked on demand** for high-stakes targets only; running both for every Bullet Set burns calls unnecessarily. The split lets the reviewer be optional. (3) The writer is **interactive coaching** (the student is in the dialogue); the reviewer is **automated critique** (the user provides JD + variant, the skill produces suggestions). Different modes, different rhythms. The two-call cost is a feature of the design, not waste. The pushback is correct that we *could* prompt a single call to do both — but the cost is collapsing two different skill shapes into one less-defensible blob.
- **Follow-ups.** What's the actual evidence the split improves outputs? Have you A/B'd it? Is the cost-of-quality argument convincing without numbers?
- **What a weak answer sounds like.** "Two prompts are better than one" — assertion without rationale.

### R5-Q6 — A student finished the full pipeline. They submit the resume. They get rejected without an interview. What does the methodology say to do?

- **Model answer.** The methodology has explicit feedback ingestion built into lesson 12's 8-step cycle. Rejection without interview means one of: (a) the resume didn't pass the 5-second human scan — fix the Summary or B1 of the relevant Bullet Set; (b) the JD was over-stretched — gap-analyze should have flagged this as ⚠️ partial fit; check the original verdict; (c) randomness — recruiter pipeline noise. The action: record the outcome in `students/<name>/applications.jsonl` (proposed in `03-elevation-roadmap.md` § C), pattern-match against the prior 3–5 rejections — if it's a pattern, run `bullet-reviewer` against the Bullet Set used. If it's noise, move on. Specifically, the methodology says: do not interpret a single rejection as a signal; interpret a pattern across 5–10 as a signal. Without the JSONL, the student has no way to know if it's a pattern.
- **Follow-ups.** What's the minimum N to call something a pattern? What if a single rejection comes with explicit feedback?
- **What a weak answer sounds like.** "Try again" — no diagnostic loop, no use of the methodology's own feedback machinery.

## Debrief framing (skill-internal — for grading)

When the interview skill writes the debrief, weight:

- **Strength signals.** Candidate volunteers a tradeoff before being asked. Candidate names a specific file path or skill name unprompted. Candidate names a real failure mode (not just a happy path). Candidate frames a design choice as "we considered X and Y, picked Y because…".
- **Weakness signals.** Generic answers without file paths. Inability to articulate *why* a design choice was made. Defaulting to "I'd add tests" without addressing what tests. Treating the writer/reviewer pair as accidental rather than intentional. Confusing POCs with cases. Missing the separate-context rule for coach/mock-interview when it's directly relevant to the question.
- **Pushback survival.** First answer is allowed to be partial. Second answer (after the pushback) should converge — restate with more precision, name a concrete tradeoff, or explicitly concede a gap.
