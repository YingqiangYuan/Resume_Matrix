## 4. README co-write outline — English, sectioned

The publish skill's Transform Step 6 walks these sections in order, asks the user the question prompts one at a time, drafts each section in ~50–120 words reflecting the user's words, then assembles the final `README.md`. **English only, regardless of the source repo's language.**

```
Section: Title and one-line tagline
  Goal: A one-line headline a hiring manager can read in 2 seconds.
  Question prompts:
    - "What do you want this repo's first impression to be?"
    - "In one sentence, what does this project let someone do?"
  Length target: 1 line + the title.

Section: What this is
  Goal: A 2-3 paragraph description of the project. Names the methodology (1+N resume matrix), the skill library (10 first-class workflow skills), and the design patterns (writer/reviewer, file-based loop). Does not name the curriculum or worked-example student — those were deleted.
  Question prompts:
    - "In one sentence, what is this project?"
    - "Who would care about it? (Be specific — 'job-seekers' is too broad.)"
    - "What's the simplest way to describe what it teaches or enables?"
    - "What's the architectural insight you'd want a senior engineer to notice?"
  Length target: 100-150 words.

Section: How it works (the skill list)
  Goal: A short tour of the 10 skills in pipeline order, naming what each consumes / produces. Three or four sentences total — this is a README, not a full doc.
  Question prompts:
    - "Of the 10 skills, which 2-3 do you want to highlight as the most interesting?"
    - "What's the one workflow you'd walk someone through in 30 seconds?"
  Length target: 80-120 words.

Section: Install and run
  Goal: The minimum command sequence from clone to first useful invocation.
  Question prompts:
    - "What's the minimum command sequence you'd give a friend who wanted to try this?"

    - "If you spent another month on this, what would you add?"
```

## 5. Hostile-scan rules for Audit mode

Run after Transform completes. The assumption is a hostile reader (engineer, hiring manager) is scanning the repo with the question "did this come from a tutorial?". Find every tell.

### 🔴 HIGH RISK (fatal on detection)

- **File-pattern flags.**
  - `**/README-cn.md` at any depth — locale-suffix READMEs are the strongest cardinal signal. The root `README.md` is the only legitimate README in the published repo.
  - `**/README-ORIGINAL.md`, `**/README-DRAFT.md`, `**/README-OLD.md`, `**/*-tutorial.*`, `**/*-course.*`, `**/*-lesson*.*`.
  - `docs/learn-*/`, `docs/tutorial*/`, `docs/lesson*/`.
  - `.claude/skills/learn-this-project-{absorb,elevate,quiz,interview,demo,publish}/` — any residual sibling skill from the meta-skill.
  - `.claude/skills/lesson-smith*/` other than `lesson-smith-learn-this-project-meta/`.
  - `examples/` directory of any shape (the curriculum directory).
  - `students/` directory of any shape (the worked-example directory).

- **README phrase flags** (case-insensitive grep on the published `README.md` and any other top-level `.md`):
  - `"this tutorial"`, `"in this tutorial"`, `"this course"`, `"in this course"`, `"the lesson"`, `"the lessons"`
  - `"as a student"`, `"the student"`, `"the learner"`
  - `"we learned"`, `"in this project we"`, `"the mentor"`, `"mentor's"`
  - `"the goal of this lesson"`, `"the goal of this course"`
  - First-person plural in a teaching context — "we built", "we designed" (singular "I built" is fine for portfolio voice).

- **Commit-message phrase flags** (grep `git log --all --format="%s%n%b"`):
  - Same phrase set as README phrase flags.
  - Plus: `"chore: add tutorial"`, `"add lesson"`, `"add course material"`, `"initial commit from template"`.

- **Git ref flags** (from `git tag --list` and `git branch --all`):
  - Tags or branches named: `tutorial-base`, `from-tutorial`, `original`, `v0-from-course`, `lesson-*`, `course-*`.

- **Residual directory flags.**
  - Any `.claude/skills/learn-this-project-*` directory other than `lesson-smith-learn-this-project-meta/`.
  - Any directory matching `*lesson-smith*` other than the bonus meta-skill.
  - `docs/learn-this-project/` (the analysis-doc directory should have been deleted in cardinal-rule § 1).

### 🟡 MEDIUM RISK (recoverable but visible)

- **Suspicious symmetry flags.** Heuristic — surface as possibility, not a hard rule:
  - Multiple SKILL.md files with identical comment banners across `.claude/skills/*/SKILL.md`.
  - Identical opening sentence patterns across multiple skills (e.g., every skill starts with "You are a...").
  - Several `SKILL.md` files with identical `argument-hint` format.
  - These signal the skills were generated from a template — true but readable as "this person uses templates" rather than "this came from a tutorial". Surface for user judgment.

- **Hygiene flags** (not teaching-specific but make the repo look unfinished):
  - `.idea/` committed (JetBrains).
  - `__pycache__/`, `*.egg-info/`, `.venv/` committed.
  - Multiple `.DS_Store` files committed.
  - Empty directories with only `.gitkeep`-style markers.

- **Frontmatter inconsistency** across the 10 first-class skills:
  - Differing `allowed-tools` shapes (some use parentheses, some don't).
  - Differing `argument-hint` formats.
  - `description` length variance > 3x between skills.

- **Outdated cross-references** in skill bodies pointing at deleted teaching paths:
  - `SKILL.md` files that mention `examples/`, `students/`, `docs/learn-this-project/`, or any deleted path.
  - Run grep on every surviving SKILL.md after deletion to catch these.

### 🔵 LOW RISK (cosmetic)

- Missing `.gitignore` entries for `.DS_Store`, `*.pyc`, `.venv/`, `.idea/`.
- README missing a license note (if the user wants to publish under one).
- Skill `description` fields longer than 240 chars (Claude Code accepts it but it makes the picker UI ugly).
- Inconsistent quote styles across SKILL.md files (`'foo'` vs `"foo"`).

### Audit output format

The publish skill's Audit mode produces a structured report:

```
🔴 HIGH RISK (N findings)
- <path or pattern>: <what was found>
  → <suggested fix command>

🟡 MEDIUM RISK (N findings)
- <path or pattern>: <what was found>
  → <suggested fix command>

🔵 LOW RISK (N findings)
- <path or pattern>: <what was found>
  → <suggested fix command>
```

The user picks which findings to apply. Transform mode does not complete until **0 🔴 HIGH findings remain** (or the user explicitly accepts them with full understanding of the consequence).
