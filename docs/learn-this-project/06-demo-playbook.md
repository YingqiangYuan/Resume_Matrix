# 06 — Demo playbook for `learn_build_resume_matrix`

This playbook covers how to **demo** this project to an audience — pick the right entry point, sequence the wow moments, hide the messy parts, tailor to the audience.

> **The single most important thing in this doc:** this is a **teaching project**, not a portfolio piece. The full repo (with `examples/01–13/`, `students/john-doe/`, `lesson-smith-*` skills, `README-cn.md` files, `README-ORIGINAL.md`) signals "this came from a tutorial" within 5 seconds to any technical audience. Before demoing to a hiring manager, run `/learn-this-project-publish` to produce a sanitized portfolio version on the user's own GitHub. **Do not demo this repo as-is to a hiring audience.** Demoing the original to peer engineers (for pedagogical discussion) or to non-technical stakeholders (who can't tell) is fine.

## Wow features

The strongest things to show, in priority order:

1. **The 1+N resume matrix in action.** Open `students/john-doe/resume.md` (the master, ~36 KB) and scroll to the Summary section. Show the **three Summary Variants side-by-side** — same person, three different positioning labels (AI Engineer / Data Analyst / Software Engineer). Then open `resume-role-1.md` and show it's the master **with sections deleted** — no rewriting. This is the architectural insight of the whole project; everything else is downstream of it.
2. **The 6-stage qualify pipeline output stack.** Navigate to `students/john-doe/experiences/from-2025-06-to-2025-09-CedarRidge-maternity-bi-agent/qualify-for-Cascadia-Health-Insights-AI-Solutions-Engineer/`. Show the file tree — every stage's output is a file (`landscape/`, `gap-analysis-cn.md`, `case-cn.md`, `execution-plan-cn.md`, `pocs/`, `tutorials/`). Each artifact stacks on the prior; by stage 4 you have 9 categories of context that the case rests on. The depth is what makes the resulting bullets defensible.
3. **The writer/reviewer pairing pattern.** Briefly open `.claude/skills/bullet-writer/SKILL.md` and `.claude/skills/bullet-reviewer/SKILL.md`. Don't dwell — just show the two SKILL.md files exist as a *pair* and explain in one sentence that writers produce general-purpose artifacts and reviewers target specific JDs. Same pattern for `mini-project-design` ↔ `mini-project-review` and `summary-writer` ↔ `summary-reviewer`. The pattern is the project's architectural signature.

If you have only 30 seconds, show #1 alone. If you have 5 minutes, show #1 + #2. If you have 15 minutes, show all three plus a brief live invocation of `/qualify-gap-analyze` against a real JD.

## Recommended sequence — golden path

### 5-minute version

1. **(0:00) Open the README.** Read out the one-line positioning: "A methodology and skill library for building a tailored, defensible US-market resume." 10 seconds.
2. **(0:10) Open `students/john-doe/resume.md`.** Scroll to the Summary section. Show three Summary Variants. Say: "Same person, three angles. The master holds everything; targeted resumes are derived by deletion only."
3. **(1:00) Show `resume-role-1.md`.** Quick scroll to confirm it's shorter than the master — just selected sections. Say: "Deriving a new resume for a specific company is minutes, not hours."
4. **(1:45) Open `examples/05-resume-matrix/README.md`.** Show the 1+N section briefly — this is the conceptual basis. ~30 seconds skim.
5. **(2:15) Cut to `students/john-doe/experiences/from-2025-06-to-2025-09-CedarRidge-maternity-bi-agent/qualify-for-Cascadia-Health-Insights-AI-Solutions-Engineer/`.** Show the file tree. Say: "Behind each Bullet Set is this stack: a JD, landscape research, gap analysis, case document, execution plan, POCs, tutorials. The bullets are defensible because the depth is real."
6. **(3:30) Open `.claude/skills/qualify-gap-analyze/SKILL.md`.** Show the first 30 lines — frontmatter + purpose. Say: "There are 10 skills like this — one per stage of the workflow. They're reusable beyond the curriculum."
7. **(4:30) Close.** Say: "The combination — methodology + reusable skills + worked example — is what makes this defensible end-to-end."

### 15-minute version

Beats 1–5 from the 5-minute version, then add:

6. **(3:30) Walk the 6-stage pipeline.** Open `examples/07-elevate-existing-project/README.md`. Scroll through the 6 stages, name each, and say what it consumes / produces. ~2 minutes.
7. **(5:30) The writer/reviewer pairing.** Open `.claude/skills/bullet-writer/SKILL.md`, then `.claude/skills/bullet-reviewer/SKILL.md`. Explain in one minute: writer is constructive, reviewer is adversarial; reviewer runs on demand for high-stakes JD-targeting. Mention the same pattern at `mini-project-design`/`-review` and `summary-writer`/`-reviewer`.
8. **(7:30) The separate-context rule.** Open `.claude/skills/qualify-coach/SKILL.md` and `.claude/skills/qualify-mock-interview/SKILL.md`. Explain in one minute: coach has memory of struggles; mock-interview must be a clean room. Hence two terminals.
9. **(9:30) Live invocation (if possible).** With Claude Code open and a real JD pasted, invoke `/qualify-gap-analyze` against the master resume. Watch it produce the gap-analysis file. **Note: only do this if it's been rehearsed and the JD has been tested with the skill.** A live failure on stage 0 wrecks the demo. If unrehearsed, skip this beat and use the time to walk the john-doe `landscape/` folder.
10. **(13:00) Close with the elevation roadmap.** Open `docs/learn-this-project/03-elevation-roadmap.md`. Scroll to the executive view (5-bullet priority list). Say: "Honest about gaps — no tests, no outcome instrumentation, validation rests on one synthetic case. Three months of next investment is here." Demonstrates self-awareness, which is the strongest signal you can give.
11. **(14:30) Wrap.** One sentence on what you'd build next + invite questions.

## Audience tailoring

| Audience | Recommended approach |
| :------- | :------------------- |
| **(a) Hiring manager, role related to this domain** (e.g., engineering for an AI tooling company, careers / HR-tech, EdTech) | 15-min version. Emphasize beats 6, 7, 10 (writer/reviewer pairing, separate-context rule, honest gap acknowledgment). Skip beat 9 unless rehearsed. |
| **(b) Hiring manager, role UNrelated to this domain** (e.g., systems engineering, embedded, infra-only) | **Honest take: skip this project entirely.** A different project will signal better for the role. If forced to use this one, run 5-min only, lead with beat 5 (the file-tree of artifacts) which signals discipline regardless of domain. |
| **(c) Peer engineer** | 15-min version with beats 7 + 8 emphasized — engineers care about the design tradeoffs (writer/reviewer split, file-based loop, separate-context discipline). Be ready for "why not X?" probes per `05-interview-playbook.md` Round 3. |
| **(d) Non-technical stakeholder** (e.g., career-services staff, an academic advisor) | 5-min version with beats 2–4 emphasized — show the user-visible value (one master → many targeted resumes by deletion only). Skip beats 6–9 entirely. Don't open SKILL.md files; they'll glaze. |

The **(b) skip-entirely** recommendation is not hedging — it's a real call. A backend-systems hiring manager doesn't care about your resume methodology project. Demo a backend systems project instead. The strongest demo is the most relevant demo.

## Do NOT show — explicit list

This list is the **highest-value section of this doc**. Before any demo to a non-team audience, confirm none of the below will appear on screen. The cardinal rule: **the audience must not detect this came from a tutorial.**

### What to do if any cardinal-rule item is still visible

**Stop the demo prep.** Either:
- (preferred) Run `/learn-this-project-publish` to produce a sanitized version on the user's own GitHub, and demo *that* repo, OR
- Open a fresh clone of this repo, manually delete the cardinal-rule items (and follow the publish-checklist's commit plan in `07-publish-checklist.md` § 3), and demo the manually-sanitized version.

**Demoing the original repo with cardinal-rule items visible turns the demo's persuasive value negative.** The audience concludes "this person ran a tutorial" instead of "this person built a methodology". That's the worst possible outcome.

## Recovery moves

What to say if a demo step fails live:

| Failure | Recovery |
| :------ | :------- |
| `students/john-doe/resume.md` opens slow or wraps badly | "This file is intentionally long — about 36KB. The size is the point: every variant lives here." Scroll to a stable visible section. |
| `/qualify-gap-analyze` errors mid-invocation | "Live invocations are model-dependent — let me show you the output from a prior run instead." Open `students/john-doe/experiences/.../gap-analysis-cn.md`. |
| The audience asks "what does the skill code actually do?" | Open the relevant `SKILL.md`. Show the frontmatter (English) and the first ~50 lines of the body. Don't try to walk all 200+ lines. |
| The audience asks about a specific edge case the playbook doesn't address | "I haven't walked that one — let me check after." Don't fabricate. |
| You accidentally open a `-cn.md` file in front of an English audience | "These are translated counterparts — let me jump to the English one." Don't apologize or explain why both exist. |
| The audience asks "is this just a tutorial?" | This means the cardinal-rule cleanup failed. Honest response: "The version I'm showing today is structured as a teaching repo because it's how I built it iteratively. The portfolio version lives at [URL of the published repo]." Then pivot to the published repo if accessible. |

## Rehearsal questions

The skill-driven rehearsal mode will ask these (or similar). Practice answering:

1. **"What problem does this project solve?"** — Don't answer "resume writing". Answer "interview-defensible resume bullets for the US tech market — backed by a methodology and a skill library, not by editing tips."
2. **"What's the most interesting design decision?"** — Pick one specifically: the file-based design-review loop, or the writer/reviewer pairing, or the 1+N matrix. Don't list all three; pick one and defend it.
3. **"What does the worked example prove?"** — That the methodology runs end-to-end on a non-trivial case. Three projects across three domains demonstrates it generalizes within reason. Acknowledge that one synthetic example isn't strong evidence and that adding 2–3 more is on the roadmap.
4. **"What would you change if you had three more months?"** — Tests + outcome instrumentation. Both are in `03-elevation-roadmap.md` § B and § C. Don't pad with vague "improve documentation".
5. **"What's the biggest unknown about whether your methodology works?"** — That it's been validated on one fictional student, not real candidates with real outcomes. The honest answer; saying it out loud demonstrates self-awareness, which is itself a strong signal.

## Closing notes

The demo should leave the audience with a single takeaway, sized for the audience:

- For an engineer: "the writer/reviewer + file-based-loop + 1+N pattern is generalizable beyond resumes — applicable to any system where a master artifact gets repeatedly tailored."
- For a hiring manager (relevant role): "this person thinks systematically about hiring + has built a tool to defend their reasoning."
- For a non-technical stakeholder: "this is what 'one master, many resumes' looks like in practice."

Don't try to leave them with three takeaways. One.
