# 03 — Elevation roadmap for `learn_build_resume_matrix`

This is the "if you had 3–6 more months" doc. The project is currently a **prose curriculum + a skill library + one fictional worked example**. The honest read: the core methodology is well thought out (writer/reviewer pairing, file-based design-review loop, 1+N resume matrix), but the project has very little evidence that the methodology has been validated at scale, almost no quality measurement, and minimal mechanical safety (no tests, no schema validation on artifacts, no link-integrity check across the cross-referencing curriculum). The elevation areas below are sorted by what would most increase the credibility of the methodology to a skeptical outside observer.

## Executive view (5-bullet priority list)

1. **Validation evidence beyond one fictional student.** Add 2–3 more worked examples (different career stages, different domains, different starting points) so the methodology can be defended as generalizable, not just "it works for john-doe".
2. **Schema and link-integrity tests for the curriculum and the artifacts.** A small `pytest` suite that asserts every SKILL.md has required frontmatter, every cross-reference resolves, every john-doe artifact promised by the curriculum exists. Catches drift cheaply.
3. **Outcome instrumentation.** A small structured-log convention (e.g., `students/<name>/log.jsonl`) capturing per-application outcomes (submitted, callback, on-site, offer, rejection-reason). Lets the methodology produce hit-rate evidence over time.
4. **An "evaluator" axis to mirror the writer/reviewer pattern at the master-resume level.** Currently writer/reviewer pairs operate on individual Bullet Sets and Summary Variants. Nothing audits the **whole master** for internal consistency (same person across all variants, no contradictory claims, version-drift after months of edits).
5. **A Chinese↔English parity check + translation hygiene.** The repo currently has `*-cn.md` files everywhere (curriculum, lessons, john-doe artifacts). When the English versions get edited, the `-cn.md` counterparts silently drift. A check (or a `lesson-smith-translate-to-en`-driven workflow) that flags parity gaps would fix this.

## Upgrade areas

### A. Validation evidence beyond `students/john-doe/`

**Current state.** One fictional student (`students/john-doe/`) with three projects (Cedar Ridge, NovaRisk, Pulse Social). All names, companies, dates are scaffolding. There is no real case study; no "we tried this with 10 real students and 7 got callbacks".

**Senior-engineer target state.** 2–4 additional worked examples covering:
- A career-changer (e.g., teacher → data analyst) — different starting point, different gap-analysis shape.
- A returning-from-leave candidate — explains how to handle resume gaps.
- An international student / immigrant — explains the visa-status constraints that gap-analyze should surface.
- At least one **real** anonymized case where the methodology was applied and the outcome is documented.

**Alternatives considered.**
- *Synthetic-only worked examples (current).* Pros: complete control over the artifact shape, no privacy concerns. Cons: outside readers reasonably suspect cherry-picking.
- *One real anonymized case study + the existing synthetic.* Pros: outside credibility. Cons: anonymization is hard, and one case isn't N.
- *Crowdsourced opt-in case studies from real users.* Pros: scales and accumulates. Cons: requires consent infrastructure and quality control.

**Knowledge prerequisites.** Anonymization patterns for resumes and project documents; how to construct fictional but internally consistent business contexts (the john-doe Cedar Ridge maternity hospital is the existing exemplar).

**Suggested learning path.**
1. Read 2–3 published case studies of career-transition success (Reverse-engineer the structure they used to make the story land.)
2. Read Jeff Atwood and Patrick McKenzie ("patio11") on writing resumes for outside readers — both have written extensively on what credibility actually looks like.
3. Apply: design 1 new synthetic student in a different career stage, write all artifacts.

### B. Test depth and coverage

**Current state.** Zero tests. No `tests/` directory. No CI. The curriculum cross-references many skills and many lesson links by path; nothing checks they still resolve.

**Senior-engineer target state.** A small `pytest` suite under `tests/`:
- `test_skill_frontmatter.py` — for every `SKILL.md`, assert `name`, `description`, `allowed-tools`, `argument-hint` exist; assert `name` matches the directory name.
- `test_curriculum_link_integrity.py` — parse every `examples/<lesson>/README.md`, extract every link to another file in the repo, assert each resolves.
- `test_john_doe_artifact_completeness.py` — for the curriculum's claims about john-doe (e.g., "Cedar Ridge has gap-analysis + case + execution-plan + landscape + pocs + tutorials"), assert each file exists.
- `test_chinese_english_parity.py` — for every `<name>.md` that has a `<name>-cn.md` sibling, assert both exist; optionally check section heading counts match (an approximation of "translation didn't drop content").
- GitHub Actions workflow runs these on every PR.

**Alternatives considered.**
- *No tests (current).* Cheap but drift is invisible.
- *Lightweight `make check` script that greps for broken links.* Cheaper than pytest, but no assertion structure and harder to extend.
- *Full property-based testing on SKILL.md schemas using Pydantic.* Heavier, but the schema becomes the source of truth and any future skill author benefits.

**Knowledge prerequisites.** `pytest` basics; markdown link parsing (`mistune` or `markdown-it-py`); minimal GitHub Actions YAML.

**Suggested learning path.**
1. Read `pytest` docs § parametrization — every test in this suite is naturally parametrized over a glob of files.
2. Read one well-tested doc-heavy repo (e.g., the Astral `uv` repo's CI) to see what testing of a non-runtime repo can look like.
3. Apply: write the four test files above. One day of work.

### C. Outcome instrumentation and feedback loop

**Current state.** The curriculum ends at "submit" (lesson 11). Nothing captures what happens after submission — callback rate, on-site conversion, offer rate, rejection reasons. The methodology has no closed loop.

**Senior-engineer target state.** A structured `students/<name>/applications.jsonl` log with one entry per application. Fields:
```json
{"date":"2026-06-15","company":"Cascadia","role":"AI Solutions Engineer",
 "experience_used":"Cedar Ridge","bullet_set":"B2","summary_variant":"A",
 "outcome":"callback","time_to_response_days":4,"rejection_reason":null,"notes":"..."}
```
Plus a small skill (`/qualify-application-log`, future) that reads this file and produces a weekly report: hit rates by Job Family, hit rates by Bullet Set, which gaps got asked about, which didn't.

**Alternatives considered.**
- *Manual prose tracking in `interviews/README.md`.* Simple but unqueryable. Currently john-doe has only a stub here.
- *JSONL (proposed).* Queryable, append-only, git-friendly.
- *Notion / spreadsheet.* Better UX but breaks the "everything in the repo" principle.

**Knowledge prerequisites.** A bit of `jq` for slicing the JSONL; the principle of structured logging.

**Suggested learning path.**
1. Read Jamie Brandon's "Local-first software" piece for the philosophy of files-as-database.
2. Read 2–3 examples of `jq` recipes against JSONL.
3. Apply: define the schema, write the skill, populate john-doe's `interviews/` retroactively.

### D. Whole-master consistency checker

**Current state.** `bullet-writer` and `summary-writer` enforce internal logic *within* one Bullet Set or Summary Variant. `bullet-reviewer` and `summary-reviewer` enforce JD-specific alignment for one variant at a time. **Nothing** audits the master resume holistically: are all Summary Variants telling the same core story with different emphasis (good), or are they contradicting each other (bad)? Has the Skills section drifted out of sync with the experiences? Is there a tech mentioned in a Bullet Set that no Summary Variant mentions?

**Senior-engineer target state.** A new skill `/master-resume-consistency` that:
- Reads the entire master resume in one pass.
- Extracts the Identity claim from each Summary Variant (e.g., "AI Engineer who...", "Data Analyst who...") and checks they describe the same person across different facets.
- Cross-references tech mentioned in any Bullet Set against the Skills section — flags untalked-about-skills and skills-without-evidence.
- Diffs the master against itself across git history — flags revisions that contradict prior claims.

**Alternatives considered.**
- *Add the consistency check inside `bullet-reviewer` / `summary-reviewer`.* Tempting but wrong — the per-variant reviewers should stay focused on their narrow JD-target job.
- *Manual mentor review once a quarter.* Works for small numbers of variants; doesn't scale past 4–5 Bullet Sets and 3+ Summary Variants.
- *Schema-extract bullets/summaries to a YAML index then run rules on that.* Heavier; requires the master to maintain a parallel index.

**Knowledge prerequisites.** Structural markdown parsing; a bit of LLM-as-judge prompt design for the "are these telling the same story?" check.

**Suggested learning path.**
1. Read the `bullet-reviewer` and `summary-reviewer` SKILL.md to see how the per-variant judge prompts are shaped.
2. Read Anthropic's eval patterns docs for grading-with-LLM.
3. Apply: write a 200-line skill that reads `resume.md`, extracts the Identity claims, and reports inconsistencies.

### E. Bilingual parity hygiene

**Current state.** ~92 `*-cn.md` files exist across `examples/` and `students/john-doe/`. When the English (or Chinese) original is edited, the counterpart silently drifts. There is a `lesson-smith-translate-to-en` skill, but no "translation parity check" skill.

**Senior-engineer target state.** A `/translation-parity-check` skill (or a tests/-level check) that:
- For every `<name>.md` with a `<name>-cn.md` sibling, parses the markdown structure of both.
- Compares: section heading counts, list-item counts, code-block counts, link counts. Mismatches flagged.
- (Stretch) Uses a small LLM grading prompt to detect "this Chinese section is missing the gist of the English section".

**Alternatives considered.**
- *Manual review.* Doesn't scale.
- *Auto-regenerate one from the other on every edit.* Loses the manual touch in translation; risks degrading both.
- *Pick one language as canonical and keep the other as a one-shot generated mirror.* A defensible choice — but the current setup has both languages in the lesson READMEs because the audience reads in both, so manual edits to both are intentional. The parity check is the right answer.

**Knowledge prerequisites.** Markdown parsing (any AST library); some prompt design if you go the LLM-grading route.

**Suggested learning path.**
1. Read 1–2 examples of bilingual docs in OSS (e.g., Vue.js docs has a process for keeping translations from drifting).
2. Apply: write the structural-comparison check first (cheap), add the LLM grading later if structural mismatches keep slipping through.

### F. Developer experience for skill authors (the meta-meta layer)

**Current state.** The repo has a `lesson-smith-learn-this-project-meta` skill (the one that wrote these docs). It generates 7 docs + 6 skills. Other meta-skills exist (`lesson-smith`, `lesson-smith-readme`, etc.). But there is no smoke test that a freshly generated skill family actually works. There is no "skill linter".

**Senior-engineer target state.** A `tests/test_generated_skill_smoke.py` that:
- After meta-skill regenerates the 6 child skills, asserts each child SKILL.md has the required structure.
- Asserts no `{{PLACEHOLDER}}` strings leaked through.
- Asserts the `EXTRA_REFS` substitution behaved correctly (zero / N entries as expected).
- Optionally invokes each child skill in a "dry-run" mode (read primary doc, print first action) to verify the skill at least loads.

**Alternatives considered.**
- *Manual smoke-test each regeneration.* Works for now (this is the first generation), but doesn't scale past 2–3 regenerations.
- *Snapshot-test the generated output against a known-good fixture.* Brittle if the meta-skill's templates evolve.
- *Lightweight assertion test (proposed).* Catches the highest-leverage drift cheaply.

**Knowledge prerequisites.** Same as area B (pytest + globbing + simple YAML / frontmatter parsing).

**Suggested learning path.**
1. Steal the `references/child-skills-spec.md` and `references/analysis-docs-spec.md` files inside the meta-skill — they're already the spec. Translate them into assertions.
2. Apply: one day of work to write the smoke test suite.

### G. Skill chaining ergonomics

**Current state.** The 6-stage qualify pipeline requires the user to manually invoke each skill, manage which terminal each runs in (especially the separate-context rule for coach vs mock-interview), and remember to hand off files between them. The `examples/07-elevate-existing-project/README.md` documents the sequence in prose, but there is no orchestration layer.

**Senior-engineer target state.** Optional helper that:
- Tracks pipeline state per `qualify-for-<company>-<role>/` folder (which stages have completed, which artifacts exist).
- Prints "next step: invoke `/qualify-execution-plan` in this terminal".
- Refuses to let the user invoke `/qualify-mock-interview` in the same conversation as the coach (or warns loudly).
- Optionally produces a one-screen status: "Stage 3 of 6, last activity 2026-06-25, blocked on: case approval".

**Alternatives considered.**
- *Documentation-only (current).* Cheapest. Relies on user discipline.
- *A wrapper skill `/qualify-next` that detects state and tells the user what to run.* Light orchestration without dictating; preserves user choice.
- *Full state machine that auto-invokes stages.* Heavier. Loses the "user is in the driver's seat" property that the methodology depends on.

**Knowledge prerequisites.** Simple filesystem scanning; understanding the artifact contracts of each stage (already documented in each SKILL.md's "Inputs" / "Outputs" section).

**Suggested learning path.**
1. Sketch the state machine on paper: 6 stages × (not-started / in-progress / done) per qualify-for folder.
2. Apply: write `/qualify-next` as a 100-line skill that reads the folder and prints next-step.

### H. Documentation and onboarding

**Current state.** `README.md` is short and high-level. `examples/README.md` indexes the curriculum. There is no "I'm new, where do I start?" doc that ties the curriculum to the skills explicitly.

**Senior-engineer target state.** A `docs/getting-started.md` (or expanded root README) that:
- Names the **two parallel artifacts** of the project (curriculum + skill library) and what each is for.
- Gives a "first 30 minutes" path (read lessons 01–05, skim 11, then invoke `/qualify-gap-analyze` against your own resume).
- Gives a "first weekend" path (work through john-doe, then start your own qualify-for folder).
- Gives a "first month" path (run the full 6-stage on your own first project).

**Alternatives considered.**
- *Leave it to the curriculum.* Works for users who actually read every lesson. Most users skim.
- *Write a short getting-started.* Cheap. Picks the highest-leverage 30-minute path.
- *Build a CLI walkthrough (`/learn-this-project-absorb`'s Orient mode does this).* Already covered by the meta-skill family — getting-started.md should still exist as the static fallback.

**Knowledge prerequisites.** None.
