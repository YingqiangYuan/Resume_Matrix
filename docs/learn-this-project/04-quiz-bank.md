# 04 — Quiz bank for `learn_build_resume_matrix`

## How these questions are designed

Questions in this bank are **discussion prompts, not fill-in-the-blank**. Each opens up a topic; a passing answer is **3–5 sentences** that names file paths AND explains the underlying principle. A one-sentence factually-correct answer is not a passing answer — that's exactly what the ⚠️ partial grade exists for.

A good answer engages with three parts:
1. **Where to look** — a specific file path, lesson number, or skill name.
2. **What** — the substance, in the learner's own teaching voice.
3. **Why** — the principle, rationale, or tradeoff that makes the answer what it is.

If a question can be answered in one sentence, the question was too narrow.

### Good vs bad question shapes

- ❌ **Bad:** "Which command creates the virtualenv?" — pure recall (`mise run venv-create`). Doesn't engage with *why* the toolchain is structured that way or *where* to verify.
- ✅ **Good:** "A new contributor asks how to get a working environment — where do you point them and how does the toolchain layer fit together?"

- ❌ **Bad:** "What does `qualify-gap-analyze` produce?"
- ✅ **Good:** "Walk through what gap-analyze produces vs what execution-plan produces, and explain why the project splits diagnosis from prescription into two skills."

- ❌ **Bad:** "What's the severity scale?"
- ✅ **Good:** "Why does the project use 🔴/🟡/🟠 instead of P0/P1/P2 or High/Med/Low? Walk through what would go wrong if you translated to one of those instead."

### Setup and toolchain

- **Q-001** [tag: runbook, difficulty: easy]
  - **Q:** A new contributor just cloned this repo and asks you what they need to type to get a working environment. Where would you point them, and what would you tell them about how the toolchain layers fit together?
  - **A:** Point them at `mise.toml` and `CLAUDE.md` at the repo root — `mise.toml` is the source of truth, `CLAUDE.md` documents the same setup for AI tooling. The two commands are `mise run venv-create` (runs `uv venv` to create `.venv/`) and `mise run inst` (runs `uv sync --all-extras`). The reason this project layers `mise` on top of `uv` is that `mise` answers *both* "which Python version?" and "what commands?", so a teammate doesn't have to memorize separate `pyenv` / `uv` / `make` stacks. Note that `pyproject.toml`'s dependency list is empty — the venv exists for forward compatibility, not because the methodology currently needs runtime code.
  - **Source:** `mise.toml`, `pyproject.toml`, `CLAUDE.md`, `docs/learn-this-project/02-runbook.md`

- **Q-002** [tag: convention, difficulty: easy]
  - **Q:** You notice `pyproject.toml` has `dependencies = []` — empty. Is that a bug, or intentional? Walk through your reasoning and where in the repo you'd confirm.
  - **A:** It's intentional. `pyproject.toml:7` shows the empty list; `uv.lock` is 152 bytes confirming no resolved packages. The project teaches a *methodology* (curriculum + agent skills + a worked example), not a Python tool — so no runtime code, no runtime deps. The scaffolding exists for forward compatibility (so future automation has a home) and to let `mise run inst` exist as a forward-looking task. The signal is: don't add deps "just in case"; the empty list is itself a teaching artifact about minimalism.

### Curriculum architecture

- **Q-003** [tag: knowhow, difficulty: medium]
  - **Q:** A learner asks "do I have to go through all 13 lessons in order, or can I jump around?" — what do you tell them, and how is the curriculum structured to support your answer?
  - **A:** The 13 lessons form 4 progressive stages: Theory (01–04), 0→1 Engineering (05–11), 1→N Asset (12), Self-sustaining Loop (13). You can read 01–04 in any order once you know your career stage, but 05–11 must be sequential because each lesson's output feeds the next (case → bullets → summary → derived resumes → submission). 12 and 13 only make sense after you've shipped one 0→1 cycle. Tell them: read 01 + (03 or 04 depending on experience level) + 05 first; then commit to running 05–11 in order on a real example before circling back to 02 and 06.
  - **Source:** `examples/README.md`, `examples/13-final-synthesis/README.md`

- **Q-004** [tag: knowhow, difficulty: medium]
  - **Q:** Lessons 03 and 04 cover new grads and experienced candidates respectively, but they don't just teach different facts — they teach different *strategies*. Walk through what changes between the two and why.
  - **A:** Lesson 03 leads with Projects because a new grad has no Work Experience to lean on; impact is described via Action + Technical Detail + Impact per project entry. Lesson 04 leads with Work Experience because the Hiring Manager is the actual reader for experienced hires (not the Recruiter), and they want outcomes — quantified accomplishments, not activities. The verb registers shift too: new grads use "Built / Designed / Implemented" while experienced can use "Owned / Refactored / Migrated / Led". Putting them in separate lessons forces the learner to pick one strategy, not blend them; the wrong verb register collapses at the first interview follow-up.
  - **Source:** `examples/03-new-grad/README.md`, `examples/04-experienced/README.md`, `docs/learn-this-project/01-knowhow-inventory.md#conventions`

- **Q-005** [tag: knowhow, difficulty: hard]
  - **Q:** Lesson 05 introduces the 1+N method and insists that derived resumes come from "deletion only, never addition or rewriting". Walk through why deletion-only matters — what fails if a student starts adding new content per derived resume?
  - **A:** Read `examples/05-resume-matrix/README.md` for the full argument. The master holds every Bullet Set angle and every Summary Variant up front; derivation is just hiding what doesn't apply. If a student starts *adding* content per company, three things break: (1) the same fact ends up phrased differently across resumes, signaling inconsistency under cross-check; (2) the master stops being the single source of truth, so edits don't propagate; (3) tailoring a new resume goes from minutes (deletion) to hours (rewriting), defeating the 1→N payoff. The whole architectural premise of the project — that scaling to many applications is cheap — collapses without deletion-only.
  - **Source:** `examples/05-resume-matrix/README.md`, `examples/12-maintain-new-projects/README.md`

- **Q-006** [tag: knowhow, difficulty: medium]
  - **Q:** Lesson 06 names three paths to project material: mentor-designed, elevate-existing, design-from-scratch. Why three? What would go wrong if the curriculum just taught one?
  - **A:** Read `examples/06-prepare-project-material/README.md`. The three paths cover three different student starting positions: someone with a mentor and ambition (path 1, fastest), someone with thin existing experience that's not interview-credible yet (path 2 — elevate; covered by lesson 07), and someone with no usable experience at all (path 3 — from-scratch; covered by lesson 08). Teaching only "elevate" would abandon students without prior experience; teaching only "from-scratch" would force students with real work history to throw it away. Naming the three paths up front forces the learner to honestly self-classify before committing to a path.
  - **Source:** `examples/06-prepare-project-material/README.md`, `examples/07-elevate-existing-project/README.md`, `examples/08-design-new-project/README.md`

- **Q-007** [tag: knowhow, difficulty: hard]
  - **Q:** Lessons 07 and 08 share the same 6-stage skeleton but differ at stage 3 (mini-project-design mode flip). Walk through the two modes — what does "elevate" preserve and lock vs what "from-scratch" leaves open?
  - **A:** Both lessons run gap-analyze → mini-project-design → execution-plan → coach → mock-interview. The mode flip happens in mini-project-design itself: `elevate` mode **locks** the business context (the real company, the real timeframe, the real team) because the student lived it — only the technical decisions get redesigned backward from the JD. `from-scratch` mode leaves business context **open** because the student hasn't lived it yet — but requires an explicit execution venue (an internship offer, an open-source project, an apprenticeship) before stage 4. The case in elevate uses past tense ("Built…"); from-scratch uses future tense ("Will build…") until the execution actually happens.
  - **Source:** `examples/07-elevate-existing-project/README.md`, `examples/08-design-new-project/README.md`, `.claude/skills/mini-project-design/SKILL.md`

- **Q-008** [tag: knowhow, difficulty: medium]
  - **Q:** Lesson 10 insists that Summary is **reverse-engineered** from Bullet Sets, not written first. Why this ordering, and what fails if a student writes the Summary first?
  - **A:** Read `examples/10-write-summary/README.md`. Summary is the *label* pointing at evidence; Bullet Sets *are* the evidence. If a student writes the Summary first, they describe who they wish they were — aspirational claims with no specific evidence behind them, which collapse at the interview follow-up "give me an example of when you…". Reversing the order forces honesty: the Summary's keywords have to be defensible by existing bullets. The master holds N Summary Variants, one per Job Family direction, and each Variant is reverse-engineered from the Bullet Sets the student has tagged as belonging to that direction.
  - **Source:** `examples/10-write-summary/README.md`, `.claude/skills/summary-writer/SKILL.md`

- **Q-009** [tag: knowhow, difficulty: medium]
  - **Q:** Lesson 11 separates GitHub (markdown source) from Google Docs (layout + mentor collab) from the final PDF. Why three stages instead of just writing the PDF in one place?
  - **A:** `examples/11-submit-and-collaborate/README.md` walks the argument. GitHub holds the **irreplaceable source** — version-controlled, branchable, recoverable. Google Docs handles **layout** (column widths, fonts, page breaks) and **mentor collaboration** (in-line comments, suggested edits) — markdown and Git aren't good at either. PDF is the **submission artifact** — what the recruiter actually receives. Combining stages loses one of: history (if you start in Docs), collaboration affordance (if you stay in GitHub), or submittability (if you stop at markdown). The split also encodes a discipline: the master in Git is canonical; the Docs version is derived; the PDF is ephemeral.
  - **Source:** `examples/11-submit-and-collaborate/README.md`

- **Q-010** [tag: knowhow, difficulty: medium]
  - **Q:** Lesson 13 says the resume is a "byproduct" of lifelong career management, not the goal. Why frame it that way, and how does the curriculum's structure reinforce that framing?
  - **A:** `examples/13-final-synthesis/README.md` makes the case. Students who treat the resume as the goal optimize for one application and burn out; students who treat it as the byproduct of a continuous "design project → close skill gaps → execute → write case → write bullets → update summary → submit → harvest feedback → next design" cycle compound indefinitely. The curriculum structure reinforces this: lesson 12 introduces the 1→N maintenance loop *before* lesson 13's flywheel, so by the time learners read 13 they've already seen that the master resume + qualify pipeline keep producing artifacts. Resume is not the unit of effort; the project + case + bullet + summary cycle is.
  - **Source:** `examples/12-maintain-new-projects/README.md`, `examples/13-final-synthesis/README.md`

### The 10 first-class workflow skills

- **Q-011** [tag: knowhow, difficulty: medium]
  - **Q:** `qualify-gap-analyze` and `qualify-execution-plan` are deliberately split into two skills, not combined. Walk through what each does and why the project keeps them separate.
  - **A:** Gap-analyze (read `.claude/skills/qualify-gap-analyze/SKILL.md`) produces a diagnosis: a 🔴/🟡/🟠-classified list of gaps between the student's current state and the target JD, with JD-quoted evidence. Execution-plan reads that diagnosis plus an approved case and produces the prescription: an execution-plan document, mini-POC scaffolds per gap, and tutorial stubs. Splitting them prevents the diagnosis from being warped by "what's easy to fix" — a combined skill would unconsciously omit gaps it has no good POC for. Separation forces the diagnosis to be honest first, the plan to be ambitious second.
  - **Source:** `.claude/skills/qualify-gap-analyze/SKILL.md`, `.claude/skills/qualify-execution-plan/SKILL.md`

- **Q-012** [tag: knowhow, difficulty: hard]
  - **Q:** `qualify-coach` and `qualify-mock-interview` must run in separate Claude Code conversations. What goes wrong if you run them in the same context, and why does the project enforce this so strictly?
  - **A:** Coach has accumulated memory of where the student struggled, what concepts had to be re-explained, what the student finally acknowledged. If the mock interviewer (same model, same conversation) inherits that memory, it softens — sympathetic to past struggles, easier on follow-up depth, generous in scoring. The student leaves thinking they're ready when they're not, and the methodology's whole point (calibrated stress test) is defeated. Both `.claude/skills/qualify-coach/SKILL.md` and `.claude/skills/qualify-mock-interview/SKILL.md` enforce a fresh-context check at invocation start. The fix is concrete: open a separate terminal / chat for mock-interview.
  - **Source:** `.claude/skills/qualify-coach/SKILL.md`, `.claude/skills/qualify-mock-interview/SKILL.md`, `docs/learn-this-project/01-knowhow-inventory.md`

- **Q-013** [tag: knowhow, difficulty: hard]
  - **Q:** `mini-project-design` and `mini-project-review` communicate only through disk files (`case-cn.md`, `review-NN.md`, `fix-NN.md`) — not shared conversation context. Walk through why this design choice was made and what it buys.
  - **A:** Read both SKILL.md files. The file-based loop gives four things: (1) **robustness** — if either terminal crashes, state persists on disk; the loop can be resumed without losing work; (2) **auditability** — each review round and each response is a permanent file artifact in the project history; (3) **tool-agnostic** — either skill could be swapped to a different model or even a human reviewer without breaking the loop; (4) **iteration speed** — long design loops (3–5 rounds typical) stay manageable because students can step away for a day and resume without conversation bloat. The reviewer is also explicitly **read-only** on everything except `review-NN.md` — prevents quiet co-authorship.
  - **Source:** `.claude/skills/mini-project-design/SKILL.md`, `.claude/skills/mini-project-review/SKILL.md`

- **Q-014** [tag: knowhow, difficulty: medium]
  - **Q:** Why does the project use a writer + reviewer pair for bullets (`bullet-writer`/`bullet-reviewer`) and summaries (`summary-writer`/`summary-reviewer`)? What's the work-split, and when does each get invoked?
  - **A:** Writers (`bullet-writer`, `summary-writer`) produce the **default** general-purpose Bullet Set or Summary Variant for a given Job Family angle. Reviewers come in **later**, when the student is targeting a specific high-stakes JD and wants the existing artifact tightened for that JD. The reviewer can operate in Mode A (in-place tweak — small keyword swaps) or Mode B (append a new JD-targeted variant — bigger reshape). This split exists because a master resume needs to be reusable across many applications: writing one new Bullet Set per application doesn't scale, so the default needs to be general-purpose, and JD-specific tuning is the rare refinement.
  - **Source:** `.claude/skills/bullet-writer/SKILL.md`, `.claude/skills/bullet-reviewer/SKILL.md`, `.claude/skills/summary-writer/SKILL.md`, `.claude/skills/summary-reviewer/SKILL.md`

- **Q-015** [tag: knowhow, difficulty: hard]
  - **Q:** `bullet-writer` enforces a B1→B4 progression: HR-readable picture, key technical decision, hardest sub-problem, ownership + cross-team impact. Why this specific ordering, and what does each bullet's role contribute?
  - **A:** Read `examples/09-write-bullets/README.md` and `.claude/skills/bullet-writer/SKILL.md`. The progression mirrors what an interviewer probes in sequence: B1 makes the project legible to a non-technical reader in 5 seconds; B2 forces the candidate to commit to one key technical decision and defend it; B3 surfaces the hardest sub-problem (where engineering judgment lives); B4 demonstrates ownership beyond the individual coding (cross-team coordination, stakeholder management). Each bullet is **separately defensible** under follow-up — an interviewer can pick any one bullet and drill 2–3 layers deep without exposing handwaving. The count flexes 2–5 depending on what the case actually supports; padding to 4 when the case doesn't support B3 produces an indefensible bullet that collapses at the first probe.
  - **Source:** `examples/09-write-bullets/README.md`, `.claude/skills/bullet-writer/SKILL.md`

- **Q-016** [tag: knowhow, difficulty: medium]
  - **Q:** A POC produced by `qualify-execution-plan` is described as a "skill drill" rather than a "fake business project". What's the distinction, and why does the methodology insist on it?
  - **A:** Read `.claude/skills/qualify-execution-plan/SKILL.md`. A POC is scoped against **one specific technical skill** the student needs to acquire — e.g., "learn Strand Agents by building a small Wikipedia QA agent". Public corpus (Wikipedia, Synthea, HuggingFace) is fine. A *fake business project* would invent a fictional company and pretend the POC is "for that company" — e.g., "build a healthcare BI dashboard for a fictional maternity hospital". The distinction matters because the student already has *one* elevated business project (from `mini-project-design`); that's where business context lives. POCs exist as **evidence pieces** the student can point to in interviews ("yes I used X — here's the repo"), not as resume entries. Conflating them wastes context budget and dilutes the elevated case.
  - **Source:** `.claude/skills/qualify-execution-plan/SKILL.md`, `examples/07-elevate-existing-project/README.md`

- **Q-017** [tag: knowhow, difficulty: medium]
  - **Q:** Walk through how an artifact stacks through the 6-stage qualify pipeline. By stage 6, what's the full input context the mock-interview has access to, and why does that matter?
  - **A:** Each stage takes [all prior artifacts] + [new input] → [new artifact] and passes everything downstream. By stage 6 (`qualify-mock-interview`), the inputs are: resume, JD, 5 landscape docs (industry / company / role / market / index), gap-analysis, case, execution-plan, POC outputs, and coach-notes. Plus the student's own conversational answers in the interview. The point is **depth compounding**: linear addition would give 9 documents of context; stacked inputs let the interviewer probe at the intersection of any pair ("you wrote in the case that you chose semantic-layer X, but the gap-analysis flagged Y as core — walk me through that choice"). A solo `mini-project-design` skill would never produce that kind of cross-stage probe.
  - **Source:** `examples/07-elevate-existing-project/README.md`, `.claude/skills/qualify-mock-interview/SKILL.md`

- **Q-018** [tag: mech, difficulty: medium]
  - **Q:** A student says "the auto-incrementing `review-NN.md` numbers seem to skip — I have review-01.md and review-03.md but no review-02.md. How does the numbering actually work?" Walk through where the logic lives and what could cause the skip.
  - **A:** Read `.claude/skills/mini-project-review/SKILL.md`. NN is auto-incremented by scanning the filesystem for the highest existing `review-NN.md` and adding one. A skip (01, 03 with no 02) almost certainly means a `review-02.md` was created and then deleted manually — possibly an aborted run. The skill doesn't repair the sequence (deliberately — it would risk overwriting an existing file). The student should either ignore the gap (numbering is informational, not load-bearing) or rename `review-03.md` to `review-02.md` themselves if they want it tidy.
  - **Source:** `.claude/skills/mini-project-review/SKILL.md`

- **Q-019** [tag: convention, difficulty: easy]
  - **Q:** The project uses 🔴 / 🟡 / 🟠 for severity instead of P0/P1/P2 or High/Med/Low. Walk through why, and what would actually go wrong if you translated to one of those.
  - **A:** Read `docs/learn-this-project/01-knowhow-inventory.md#conventions` and `.claude/skills/qualify-gap-analyze/SKILL.md`. The emoji scale is **job-search-specific**: 🔴 Core blocks the phone screen, 🟡 Important weakens the on-site, 🟠 Nice-to-have is polish. P0/P1/P2 are loaded with software-engineering connotations (incidents, outages); using them would import the wrong urgency model and mislead students about prioritization. High/Med/Low is generic and loses the specific phone-screen/on-site/polish staging that lets students plan against interview-stage deadlines.
  - **Source:** `.claude/skills/qualify-gap-analyze/SKILL.md`, `docs/learn-this-project/01-knowhow-inventory.md`

- **Q-020** [tag: knowhow, difficulty: medium]
  - **Q:** A user asks: "Can I just use `bullet-writer` without first running `qualify-gap-analyze` or `mini-project-design`?" — what do you tell them and what's the tradeoff?
  - **A:** Yes, technically — `bullet-writer` only requires a master resume path and a case document. The case can be hand-written (e.g., a real project the student already understands deeply). But the methodology assumes the case has been **interrogated** first: gap-analyze surfaces what the JD actually rewards, and `mini-project-design`'s review loop pressure-tests the case. Without those upstream stages, `bullet-writer` will faithfully compress whatever case it gets — including a thin or hand-wavy case, producing thin or hand-wavy bullets. The skill chain is decoupled (each skill works standalone) but the depth compounds when run in sequence.
  - **Source:** `.claude/skills/bullet-writer/SKILL.md`, `examples/06-prepare-project-material/README.md`

### Conventions and design choices

- **Q-025** [tag: convention, difficulty: medium]
  - **Q:** Why does every Summary Variant and (usually) every Bullet Set carry an inline `> **Rationale**` blockquote? What's that block for, and what fails if a student deletes them to make the master tidier?
  - **A:** Read `.claude/skills/summary-writer/SKILL.md` and look at any Summary Variant in `students/john-doe/resume.md`. The Rationale block records *why* this verb, this noun, this Identity, this tech-list ordering. Three months later when the student edits the master, they can read the rationale and decide whether the original logic still holds — without it, edits become arbitrary and the master degrades. Mentor reviews also land directly on the rationale (in Google Docs collaboration). Deleting the blocks makes the master 20% shorter but loses the metadata that lets future edits stay coherent.
  - **Source:** `.claude/skills/summary-writer/SKILL.md`, `students/john-doe/resume.md`, `examples/10-write-summary/README.md`

- **Q-026** [tag: convention, difficulty: easy]
  - **Q:** Why does the project use third-person implicit-subject phrasing for bullets ("Built a BI agent") rather than first-person ("I built a BI agent")?
  - **A:** Read the bullet examples in `students/john-doe/resume.md` and the rules in `.claude/skills/bullet-writer/SKILL.md`. Three reasons: (1) **convention** — professional resume writing convention in the US, signals genre fluency; (2) **density** — bullets are space-constrained and "I" eats a word for no information gain (the subject is obvious); (3) **ATS / scanning** — recruiters parse the *verb-led* pattern in 5 seconds; "I" breaks that rhythm. The same rule applies to Summaries. Chat dialogue and rationale blocks may use first-person normally.
  - **Source:** `.claude/skills/bullet-writer/SKILL.md`, `students/john-doe/resume.md`

- **Q-027** [tag: convention, difficulty: easy]
  - **Q:** Why does the repo have `*-cn.md` files alongside plain `.md` files in so many places? What's the convention and where would you go to confirm it?
  - **A:** `-cn.md` suffix marks Chinese content; plain `.md` (or English content inside `.md`) is English. The convention is documented in the meta-memory (`MEMORY.md` cites `chinese_english_file_naming.md`) and is consistently applied across `examples/<lesson>/`, `students/john-doe/experiences/`, and `.claude/skills/`. One exception: `SKILL.md` frontmatter is **always English** regardless of body language — that's what Claude Code's skill-matching engine reads. The bilingual setup exists because the audience reads both languages and the curriculum is taught in both; the parity isn't auto-checked (see `03-elevation-roadmap.md` § E for that gap).
  - **Source:** `MEMORY.md`, `examples/05-resume-matrix/README-cn.md`, `examples/05-resume-matrix/README.md`

- **Q-028** [tag: knowhow, difficulty: medium]
  - **Q:** Verb registers are calibrated by experience level — new grads can't use "Architected", "Spearheaded", "Pioneered". Walk through why this rule exists and what happens if a student violates it.
  - **A:** Read `examples/03-new-grad/README.md`, `examples/04-experienced/README.md`, and `.claude/skills/bullet-writer/SKILL.md`. Verbs encode *claimed role*. "Architected" implies overall system design ownership; "Spearheaded" implies leading a team or initiative; "Pioneered" implies novelty over existing approaches. A new grad with a class project can't credibly back any of these — the first interview follow-up ("walk me through how you architected this") exposes the gap and tanks the interview. The rule isn't aesthetic; it's about avoiding claims the case can't defend. New grads have a still-strong verb pool: "Built", "Designed", "Implemented", "Wrote", "Investigated", "Studied".
  - **Source:** `.claude/skills/bullet-writer/SKILL.md`, `examples/03-new-grad/README.md`, `examples/09-write-bullets/README.md`

### Series-style and cross-skill comparisons

- **Q-029** [tag: series, difficulty: hard]
  - **Q:** Compare `bullet-reviewer` and `mini-project-review`. They're both "review" skills with critical-hiring-manager / critical-mentor framing — but they differ in important ways. Walk through what each reviews, how each interacts with the corresponding writer, and the design reason for the differences.
  - **A:** **`mini-project-review`** is **read-only** on the case + design-fix files. Communicates exclusively through `review-NN.md` files on disk. Cannot edit the case. Runs in a **separate terminal** from `mini-project-design`. **`bullet-reviewer`** **edits the master resume directly** (with explicit student approval) — either in-place (Mode A) or by appending a new variant (Mode B). Communicates through chat dialogue with the student, not through files. The asymmetry exists because the case is the *spine of the methodology* (deserves the protection of read-only review and a long file-based loop) while a Bullet Set is the *leaf artifact* (cheap to edit, easy to revert via git). The reviewer's authority scales with the artifact's downstream blast radius.
  - **Source:** `.claude/skills/mini-project-review/SKILL.md`, `.claude/skills/bullet-reviewer/SKILL.md`

- **Q-030** [tag: series, difficulty: hard]
  - **Q:** Walk through the four `qualify-*` skills (`gap-analyze`, `execution-plan`, `coach`, `mock-interview`) as a pipeline. What does each contribute, and why is the project's investment in keeping them as **four separate skills** rather than one combined skill?
  - **A:** `gap-analyze` diagnoses (severity-classified gap list); `execution-plan` prescribes (POCs + tutorials + week-by-week schedule); `coach` teaches (dialogue per concept, with progress tracking); `mock-interview` stresses (clean-context production-grade probe). Keeping them separate lets each skill be invoked **on demand**: a student with a clear gap-analysis can re-run execution-plan with a different timeline; a student returning after a month can re-invoke coach without re-running diagnosis; a student preparing for a different company can re-run mock-interview with fresh inputs. A combined skill would force students through the whole pipeline every time. The split also lets each skill be **graded independently** — gap-analyze's diagnosis is judged against the JD; execution-plan's prescription is judged against case + gap; coach's success is judged by the student's acknowledgment; mock-interview's success is judged by the debrief verdict. Combining them collapses the grading.
  - **Source:** `.claude/skills/qualify-gap-analyze/SKILL.md`, `.claude/skills/qualify-execution-plan/SKILL.md`, `.claude/skills/qualify-coach/SKILL.md`, `.claude/skills/qualify-mock-interview/SKILL.md`, `examples/07-elevate-existing-project/README.md`

- **Q-031** [tag: series, difficulty: medium]
  - **Q:** The `lesson-smith-*` family of skills (14 variants) is described as "supporting infrastructure, not subject matter" in the inventory. Why are they kept separate from the 10 first-class skills, and what would change if they were promoted to first-class?
  - **A:** Read the table in `docs/learn-this-project/01-knowhow-inventory.md#bucket-e--supporting-infrastructure`. The `lesson-smith-*` skills *produce the curriculum itself* — they're tools the author uses to maintain the teaching content, not tools the student uses to learn. Promoting them to first-class would conflate the audience: students would see 24 skills in `/`, half of which they'd never need. Worse, the publish-step (see `07-publish-checklist.md`) explicitly **deletes** the entire `lesson-smith-*` family — they signal "this came from a tutorial". Keeping them separate from the 10 first-class skills makes that deletion clean: the boundary is clear in the inventory. **WHY (best guess; verify with project owner):** keeping `.claude/skills/lesson-smith*` in `.gitignore` also reflects this — they're regeneratable artifacts, not source-of-truth.
  - **Source:** `docs/learn-this-project/01-knowhow-inventory.md#bucket-e--supporting-infrastructure`, `.gitignore`, `docs/learn-this-project/07-publish-checklist.md`

### Methodology principles

- **Q-032** [tag: knowhow, difficulty: medium]
  - **Q:** Lesson 02 calls the ATS "a database, not a red-eyed judge" and debunks five myths. Walk through the **Reader-Compliant principle** that comes out of that lesson, and how it shapes downstream lessons.
  - **A:** Read `examples/02-ats/README.md`. The ATS doesn't auto-reject keywords, doesn't compute a "compliance score", doesn't get fooled by white-font tricks, can't be prompt-injected. It's a database storing what recruiters search through. The *real* reader is a human scanning for 5 seconds. The Reader-Compliant principle is: write for the human's 5-second scan first; the database-friendly formatting follows naturally. Downstream this shapes lesson 09 (B1 = HR-readable picture in one bullet — direct application of the principle), lesson 10 (Summary = 2-line label, scannable), lesson 11 (1-page PDF for junior, easy to scan), and the bullet/summary writers' verb-density rules.
  - **Source:** `examples/02-ats/README.md`, `examples/09-write-bullets/README.md`, `examples/10-write-summary/README.md`

- **Q-033** [tag: knowhow, difficulty: medium]
  - **Q:** Lesson 07 (and 08) call the 6-stage pipeline a "backward design from JD". Walk through what "backward" means here — what flows backward, and what fails if you try to design the case "forward" from your interests?
  - **A:** Read `examples/07-elevate-existing-project/README.md`. The JD is the *target*; everything is designed backward toward it. Gap-analyze starts from the JD's quoted requirements and works back to what's missing in the student's current state. Mini-project-design (elevate mode) takes the student's real experience and re-scopes the technical decisions backward to close those specific gaps. Forward design ("what's an impressive project I could build?") produces hot-air projects that show off the student's enthusiasms but don't match what the JD rewards. Backward design produces interview-credible projects: every choice in the case has a JD-quote backing it.
  - **Source:** `examples/07-elevate-existing-project/README.md`, `examples/08-design-new-project/README.md`, `.claude/skills/mini-project-design/SKILL.md`

- **Q-034** [tag: knowhow, difficulty: hard]
  - **Q:** The methodology splits Summary into **Identity + Strength + Evidence**. Walk through what each part contributes and what a Summary missing one of the three would look like.
  - **A:** Read `examples/10-write-summary/README.md`. **Identity** is the role label — "AI Engineer", "Data Analyst", "Senior Backend Engineer". Without it the reader doesn't know what bucket to put the candidate in. **Strength** is the differentiating angle — "with healthcare-domain LLM eval depth", "with hands-on Postgres logical-replication experience". Without it the candidate is generic. **Evidence** is the proof — "built X that did Y" — pointing at one specific artifact (typically a Bullet Set). Without it the claims are aspirational. Each Summary Variant in the master nails all three. Missing Identity = unfocused; missing Strength = commodity; missing Evidence = aspirational. The Variants live side-by-side in the master so the **same person** can be Identity-A for one JD and Identity-B for another — different facets of one consistent story, not three different stories.
  - **Source:** `examples/10-write-summary/README.md`, `.claude/skills/summary-writer/SKILL.md`, `students/john-doe/resume.md`

- **Q-035** [tag: knowhow, difficulty: medium]
  - **Q:** The curriculum talks about resumes as a **byproduct of a flywheel**, not a one-shot artifact. Walk through the flywheel — what spins, what compounds, and where would you point a student who wants to start their first revolution?
  - **A:** Read `examples/13-final-synthesis/README.md`. The 8-step cycle: design project (from JD) → identify skill gaps → execute → write case → write bullets → update summary → derive resume → submit → harvest feedback → next design. Each turn produces: a deepened skill set, a new case in the experiences folder, new Bullet Sets in the master, possibly a new Summary Variant if the angle is genuinely new, and structured feedback (callbacks, rejections, interview transcripts) that informs the next design. What compounds: the master resume grows in evidence; the student's interview-credibility grows because they've now defended this case under live questions; the skill list grows because each project closed real gaps. Where to start: lessons 01–05 (theory + matrix mental model), then dive into 07 or 08 on a real first project.
  - **Source:** `examples/13-final-synthesis/README.md`, `examples/12-maintain-new-projects/README.md`

### Edge cases and gotchas

- **Q-036** [tag: knowhow, difficulty: medium]
  - **Q:** A student has run `bullet-reviewer` in Mode B for three different JDs against the same experience, so the master now has Bullet Set N (original) + three JD-targeted variants. They ask "do I keep all four forever?" What do you tell them, and what trade-off are you balancing?
  - **A:** Yes — keep all four. The master's whole point (per lesson 05's 1+N method) is to hold every variant so derived resumes are deletion-only. Pruning the master to be tidier breaks the matrix: the next time a similar JD comes along, the student has to re-invoke the writer instead of reusing a stored variant. The tradeoff is: master grows long over time (sometimes >50 KB for an experienced candidate after many applications), but that's deliberate. Use the Rationale blockquotes to remember why each variant exists. The only legitimate reasons to delete a variant: (a) the underlying case has been rewritten and the old variant no longer matches reality, or (b) the variant's Job Family direction was abandoned.
  - **Source:** `.claude/skills/bullet-reviewer/SKILL.md`, `examples/05-resume-matrix/README.md`, `examples/12-maintain-new-projects/README.md`

- **Q-037** [tag: knowhow, difficulty: hard]
  - **Q:** A student finishes `qualify-mock-interview` and the verdict is **not ready** — five "go back to coach" items surfaced. They ask: "should I re-run the same mock interview after coaching those, or move on to a different interview pass?" Walk through what the methodology recommends and why.
  - **A:** Read `.claude/skills/qualify-mock-interview/SKILL.md`. Re-run the **same** mock interview round (or a fresh round with the same JD/case) after closing the coach items — but in a **fresh conversation context** so the new interviewer doesn't remember the prior round's struggles. The point of re-running is to verify the gaps actually got closed under pressure; jumping to a different interview pass would test different things and leave the original gaps unverified. The numbering convention (`mock-interview-1.md`, `-2.md`, `-3.md`) supports this — each round is a separate artifact, with its own debrief, and the trajectory of debrief verdicts across rounds is itself the calibration signal.
  - **Source:** `.claude/skills/qualify-mock-interview/SKILL.md`, `.claude/skills/qualify-coach/SKILL.md`

- **Q-038** [tag: knowhow, difficulty: medium]
  - **Q:** The repo has `README-ORIGINAL.md` at the root next to `README.md`, and they differ only in title casing. Why does this file still exist, and what would you do with it before publishing the project?
  - **A:** **WHY (best guess; verify with project owner):** it's the historical first draft preserved when the English version was finalized; not load-bearing. Before publishing the repo as a portfolio piece (see `07-publish-checklist.md` § cardinal-rule deletes), `README-ORIGINAL.md` is on the delete list — it's a teaching artifact: an obvious "this came from somewhere" tell that breaks the cardinal "don't be detected as a tutorial" rule. The publish-skill will list it in the dry-run preview and delete on consent.
  - **Source:** `README-ORIGINAL.md`, `docs/learn-this-project/07-publish-checklist.md`

- **Q-039** [tag: mech, difficulty: medium]
  - **Q:** A learner is invoking `/qualify-execution-plan` and it errors out saying the gap analysis is missing. They believe they ran `/qualify-gap-analyze` already. Walk through what's most likely wrong and how you'd diagnose it.
  - **A:** Read both skills' SKILL.md "Inputs" sections. Most likely: gap-analyze did run, but wrote `gap-analysis-cn.md` into a different folder than the one execution-plan is now reading. Both skills resolve paths relative to the current working `qualify-for-<company>-<role>/` folder. If the student was in `qualify-for-A/` for gap-analyze and is now in `qualify-for-B/`, the file isn't there. Diagnose: ask the student to `pwd` and to `ls` the qualify-for folder. Either re-run gap-analyze in the right folder or move the existing file.
  - **Source:** `.claude/skills/qualify-gap-analyze/SKILL.md`, `.claude/skills/qualify-execution-plan/SKILL.md`, `docs/learn-this-project/02-runbook.md`

- **Q-040** [tag: knowhow, difficulty: hard]
  - **Q:** The whole methodology presumes the user has *one master resume* on GitHub. A new user asks: "Why GitHub instead of Notion / Docs / a plain file on my laptop?" Walk through the rationale.
  - **A:** Read `examples/11-submit-and-collaborate/README.md`. Three reasons: (1) **Version control** — every edit is recoverable; the master grows over years and any single bad rewrite can be diffed and rolled back. (2) **Branching** for risky restructures — try a major reorganization on a branch, revert if it doesn't land. (3) **Externalized backup** — a laptop failure doesn't lose the master. Notion isn't text-diffable; Docs has revision history but isn't grep-able or scriptable; a plain laptop file has no backup. The methodology layers Google Docs *on top of* GitHub for collaboration (mentor in-line comments) and PDF *on top of* Docs for submission — but GitHub is the source of truth.
  - **Source:** `examples/11-submit-and-collaborate/README.md`

- **Q-041** [tag: knowhow, difficulty: medium]
  - **Q:** Walk through the difference between an `executed-case.md` and a `case-cn.md` in `students/john-doe/experiences/from-2026-04-to-2026-09-pulse-social-feed-ranker/`. Why do both exist, and which one is the "real" case?
  - **A:** Pulse Social is the worked example for `from-scratch` mode (lesson 08). At case-design time (before execution), the student writes `case-cn.md` in future tense ("I will build…") — that's the **design** document, used by `qualify-gap-analyze` and `qualify-execution-plan` to plan the project. After the project actually gets built (over 5 months on the timeline in the folder name), the student writes `executed-case.md` in past tense ("Built…") — that's the **post-execution** case, used by `bullet-writer` to compress into resume bullets. Both are "real"; they describe the same project at two different lifecycle moments. Elevate mode (Cedar Ridge) only has the elevated `case-cn.md` because the project was already executed when elevation began.
  - **Source:** `students/john-doe/experiences/from-2026-04-to-2026-09-pulse-social-feed-ranker/`, `examples/08-design-new-project/README.md`

- **Q-042** [tag: knowhow, difficulty: hard]
  - **Q:** The 10 first-class skills are deliberately *one-purpose* — each does one thing. The lesson-smith family has higher-level skills like `lesson-smith-all` that do multiple things at once. Walk through the design tension between one-purpose and orchestration skills, and where each pattern is the right answer.
  - **A:** Read `.claude/skills/lesson-smith-all/SKILL.md` (an orchestration skill) vs `.claude/skills/qualify-gap-analyze/SKILL.md` (one-purpose). The first-class qualify-* skills stay one-purpose because the **user is the orchestrator** — they're in the driver's seat of their career strategy, and need to decide when to re-run gap-analyze, when to skip to execution-plan, when to loop coach-mock_interview. Orchestration would dictate. The lesson-smith skills are used by the **author maintaining the curriculum**, where batch operations ("regenerate everything in this lesson folder") save real time and the maintainer wants the dictation. The pattern: one-purpose when the user needs judgment, orchestration when the user just wants results. The 6-stage pipeline could grow a `/qualify-next` orchestration helper (see `03-elevation-roadmap.md` § G) — but only as an optional helper, never as a replacement for the one-purpose skills.
  - **Source:** `.claude/skills/qualify-gap-analyze/SKILL.md`, `.claude/skills/lesson-smith-all/SKILL.md`, `docs/learn-this-project/03-elevation-roadmap.md#g-skill-chaining-ergonomics`
