# 01 — Knowhow inventory for `learn_build_resume_matrix`

## Project at a glance

`learn_build_resume_matrix` is a **teaching project**: it bundles a 13-lesson curriculum and a fleet of 10 first-class agent skills that together teach a methodology for building a tailored, defensible resume for the US job market. The core mental model is the **1+N resume matrix** — one master resume holding multiple Summary Variants and Bullet Sets, from which any number of company-targeted resumes are derived by deletion only. The project is split into two interlocking subjects: (1) the abstract workflow (how to diagnose, design, learn, drill, write, and submit) and (2) the agent skills that operationalize each stage of that workflow. The skills are designed to be reusable beyond the curriculum — they work on any case + JD pair.

The repo has no runtime code beyond `pyproject.toml`'s scaffolding; every artifact is either prose (curriculum lessons), an agent skill (`.claude/skills/`), or a worked example (`students/john-doe/`).

### Bucket B — Curriculum (`examples/`)

The 13 lessons form a 4-stage learning arc: **Theory (01–04) → 0→1 Engineering (05–11) → 1→N Asset (12) → Self-sustaining Loop (13)**.

#### `examples/01-hiring/` — Who actually reads your resume
- **What:** Three hiring scenarios (campus recruiting, direct apply at SMB, experienced hire). Roles: Recruiter, Hiring Manager, ATS. Insight: new grads compete with experienced hires in the SMB direct-apply pool.
- **Why:** Frames every later lesson — the reader determines the criteria. You can't write a "good resume" abstractly; you write for a specific reader in a specific scenario.

#### `examples/02-ats/` — ATS in the AI era
- **What:** Demystifies the ATS. Five myths debunked (auto-reject keywords, ATS-compliant score, white-font trick, prompt injection). Introduces the **Reader-Compliant principle**: write for humans scanning for 5 seconds.
- **Why:** Most candidates over-engineer for the ATS (a database, not a judge) and under-engineer for the human (a scanner with 5 seconds). Inverts the priority.

#### `examples/03-new-grad/` — How new grads write a resume
- **What:** Structure: Contact → Summary (if targeted) → Education → Skills → Projects → Work Experience. Action + Technical Detail + Impact for each project entry. Multiple resumes for different directions.
- **Why:** New grads can't lean on Work Experience, so Projects becomes the central section. The Action+Detail+Impact pattern is the smallest unit of evidence.

#### `examples/04-experienced/` — How 1–5 year experienced candidates write a resume
- **What:** Shift from "what I did" to "what I accomplished". Work Experience becomes core. Education drops to bottom. Quantified impact is the new currency.
- **Why:** The reader of an experienced resume is the Hiring Manager, not the Recruiter. They want outcomes. The verb register and the quantification register both have to shift.

#### `examples/05-resume-matrix/` — The 1+N method
- **What:** Maintain one ridiculously long master resume holding **multiple Summary variants** (one per Job Family) and **multiple Bullet Sets** per experience (one per angle). Derive any targeted resume by **deletion only**, never addition.
- **Why:** This is the architectural lesson of the whole curriculum. Addition (writing a new resume each time) doesn't scale; subtraction does. Also: keeping all variants side-by-side forces internal consistency — a single applicant telling one core story with different emphasis, not pretending to be 3 different people.

#### `examples/06-prepare-project-material/` — Three paths to bullet material
- **What:** Method 1 — mentor-designed project. Method 2 — elevate thin existing experience. Method 3 — design new project from scratch. All three assume a completed "Understand Landscape" stage.
- **Why:** Bullets are downstream of cases. Cases come from one of three upstream sources. Naming the three paths makes the choice explicit.

#### `examples/07-elevate-existing-project/` — 6-stage elevation pipeline
- **What:** Step 1 understand-landscape → Step 2 qualify-gap-analyze → Step 3 mini-project-design + mini-project-review (loop) → Step 4 qualify-execution-plan → Step 5 qualify-coach → Step 6 qualify-mock-interview. Walks the **John Doe / Cedar Ridge** maternity BI Agent example end to end.
- **Why:** Method 2 from lesson 06. "Elevate" mode locks the company/timeframe/team (the lived facts) and re-scopes the technical decisions backward from the target JD. Turns shallow experience into interview-credible experience.

#### `examples/08-design-new-project/` — Same 6-stage pipeline, from-scratch mode
- **What:** Same skeleton as 07, only the mode in Step 3 flips from `elevate` to `from-scratch`. The case uses "I will" tense (forward-looking). An **execution venue** (internship offer, open-source maintainership, apprenticeship) is mandatory before starting. John Doe / Pulse Social example.
- **Why:** Method 3 from lesson 06. For students with too little experience to elevate, the from-scratch path. The execution-venue gate exists because a project that can't be plausibly executed is wasted scope.

#### `examples/09-write-bullets/` — Compress case → 3–4 bullets
- **What:** B1 = HR-readable project picture, B2 = key technical decision, B3 = hardest sub-problem, B4 = ownership + cross-team impact. Count flexes 2–5 depending on what the case supports. Each bullet must defend itself under interviewer follow-ups.
- **Why:** Bullets are interview-defensible compressions of cases. The B1–B4 progression mirrors what an interviewer probes: picture → decisions → hardest part → ownership.

#### `examples/10-write-summary/` — Reverse-engineer Summary from bullets
- **What:** Summary is a 2-line positioning label = **Identity + Strength + Evidence**, not autobiography. Master holds N variants, one per Job Family direction. **Reverse-engineered** from Bullet Sets already in the master (not invented).
- **Why:** Bullets are the evidence; Summary is the label that points at the evidence. Writing Summary first leads to vague aspirational claims; reversing the order forces honesty.

#### `examples/11-submit-and-collaborate/` — GitHub → Google Docs → PDF
- **What:** Pipeline: master on GitHub (source) → Google Docs (layout + mentor collab) → PDF (submitted). 1 page for new grads / junior, more for senior. GitHub holds the irreplaceable source; Google Docs handles layout and mentor markup.
- **Why:** Decouples authoring (markdown, version-controlled) from layout (Docs, visual). Mentor collaboration belongs in Docs (in-line comments); long-term source belongs in Git (history, branches, recoverability).

#### `examples/12-maintain-new-projects/` — 1→N maintenance loop
- **What:** After the initial 0→1 push, every new experience follows an 8-step cycle: create folder → write case → optionally run 6-stage pipeline → run bullet-writer → run summary-writer → update Skills → derive targeted resumes → submit. Onboarding 1 experience ≈ 1–2 days; new applications drop to 30–60 min.
- **Why:** The whole project pays off in 1→N. The 0→1 setup is expensive; the per-application marginal cost should be trivial. If a new application still takes hours, the master isn't doing its job.

#### `examples/13-final-synthesis/` — Closing the flywheel
- **What:** No new tools. 4 progressive stages stitched together: theory → 0→1 → 1→N → flywheel. Resume as **byproduct** of lifelong career management.
- **Why:** Reframes the curriculum: students who treat the resume as the goal will burn out; students who treat it as the byproduct of a career-management loop will compound indefinitely.

#### `examples/README.md`
- **What:** Index of all 13 lessons with one-line topic descriptions.
- **Why:** Entry point. New readers should open this file first.

### Bucket C — First-class workflow skills (`.claude/skills/`)

These 10 skills are the **subject matter** of the project. They operationalize the curriculum and are designed to work on any (case, JD) pair, not just the John Doe example. Each is a one-purpose skill with explicit inputs, outputs, and pairing rules.

#### `qualify-gap-analyze`
- **What:** Diagnoses the gap between a student's current state (resume + experience) and a target JD. Produces one honest gap audit classified 🔴 Core / 🟡 Important / 🟠 Nice-to-have, with per-gap evidence quoted from the JD and the current state.
- **Why:** Most candidates over-estimate their own fit. An external diagnostic that quotes the JD verbatim and counters with what the current resume actually shows forces calibration. Critically, gap-analyze does **not** also propose a fill plan — that's `qualify-execution-plan`'s job, and the split exists to prevent diagnosis from being warped by what's easy to fix.
- **Key files:** `.claude/skills/qualify-gap-analyze/SKILL.md`, `.claude/skills/qualify-gap-analyze/references/`.
- **Outputs:** `gap-analysis-cn.md` (or `.md`) with relevance check, breakdown table, deep-dive sections per severity, cross-gap entanglement notes, verdict, handoff notes.
- **Pairs with:** `mini-project-design` (reads the gap to guide case design); `qualify-execution-plan` (reads the gap to scope POCs).
- **Gotchas:** Severity is 🔴🟡🟠 (not P0/P1/P2 or High/Med/Low) because the semantics are job-search-specific: 🔴 blocks the phone screen, 🟡 weakens on-site, 🟠 is polish. Don't translate.

#### `mini-project-design`
- **What:** Designs a 3–6 month project that, when built or deeply understood, qualifies a student for a target JD. Two structural modes — `elevate` (locked business context, deepen tech decisions) and `from-scratch` (forward-looking, requires execution venue). Two execution modes — `initial` (first draft) and `loop` (file-based refinement with mini-project-review).
- **Why:** The case document is the unit of evidence for the entire downstream pipeline (bullets, summary, interview). It needs to be designed deliberately, not assembled accidentally. The `elevate` vs `from-scratch` mode split exists because a student with thin experience needs `elevate`, and a student with no relevant experience needs `from-scratch`; conflating them produces vague cases.
- **Key files:** `.claude/skills/mini-project-design/SKILL.md` + extensive `references/` and `templates/`.
- **Outputs:** `case-cn.md` or `case.md`. In loop mode, also reads `review-NN.md` from mini-project-review and writes `fix-NN.md` responses.
- **Pairs with:** `mini-project-review` (the file-based design-review loop — see Design Choice 3).
- **Gotchas:** The two terminals **must not** share conversation context. Design and review communicate only through disk files.

#### `mini-project-review`
- **What:** Independently reviews a case produced by `mini-project-design` along feasibility / depth / JD alignment / mode-specific axes. Issues a verdict of `approve` / `approve-with-revisions` / `redesign`.
- **Why:** Solo case design degenerates into ego-driven scope. An external reviewer with a structured rubric catches over-claiming, under-scoping, and missed JD signals. Critically, the reviewer is **read-only** on everything except its own `review-NN.md` output — it cannot edit the case or the fix files, which prevents the reviewer from quietly becoming a co-author.
- **Key files:** `.claude/skills/mini-project-review/SKILL.md`.
- **Outputs:** `review-NN.md` (English) or `review-NN-cn.md` (Chinese). NN auto-incremented from filesystem state.
- **Pairs with:** `mini-project-design` (asymmetric: review writes review-NN.md; design reads it and responds with fix-NN.md).

#### `qualify-execution-plan`
- **What:** Given a gap analysis plus an approved case, produces the concrete execution plan: an `execution-plan-cn.md` document with cross-entanglement matrix and week-by-week schedule, plus one **mini-POC scaffold** per gap and one **tutorial stub** per gap.
- **Why:** The case is the *destination*; the execution plan is the *bridge*. POCs are scoped against the case's specific tech choices, not the raw JD — this matters because a JD might mention "RAG" generically, but the case might commit to a specific RAG stack, and the POC has to drill that exact stack to be defensible.
- **Key files:** `.claude/skills/qualify-execution-plan/SKILL.md`.
- **Outputs:** `execution-plan-cn.md` (main plan), `pocs/poc-NN-<slug>/README-cn.md` per gap, `tutorials/NN-<slug>-cn.md` stubs.
- **Pairs with:** `qualify-coach` (uses POCs + tutorials); `qualify-mock-interview` (uses gap severity for probe-priority).
- **Gotchas:** A POC is a **skill drill**, not a fake business project. "Learn Strand Agents by building a small Wikipedia QA agent" is correct; "build a healthcare BI dashboard for a fictional maternity hospital as a POC" is wrong — that conflates POC with case.

#### `qualify-coach`
- **What:** Interactive concept-by-concept teaching that walks the student through skill gaps identified by `qualify-execution-plan`. **Dialogue mode only** (never lecture mode). After each explanation, asks verification questions, adapts on weakness, and only advances when the student acknowledges the concept.
- **Why:** Knowledge that the student can't paraphrase doesn't survive the mock interview. The dialogue gate forces re-engagement on each concept; the file-based progress tracker lets long learning paths span multiple sessions without losing state.
- **Key files:** `.claude/skills/qualify-coach/SKILL.md`.
- **Outputs:** `coach-notes/concept-<slug>.md` (one per acknowledged concept); running `coach-notes/_progress-cn.md`.
- **Pairs with:** `qualify-mock-interview` — and the pairing is **separate-context** (see Design Choice 2).
- **Gotchas:** The coach has memory of student struggles; that memory must not bleed into the mock interview. Always run the mock in a fresh terminal.

#### `qualify-mock-interview`
- **What:** Pressure-test mock interview. Plays a senior interviewer at the target JD's company. Probes 2–3 layers deep on every answer. **Never teaches mid-interview.** Produces a debrief with per-concept verdict and a prioritized "go back to coach" list.
- **Why:** Coach sessions confirm the student understands; mock interview confirms the student can defend. They test orthogonal things. The "never teach mid-interview" rule prevents the interview from collapsing into another coaching session.
- **Key files:** `.claude/skills/qualify-mock-interview/SKILL.md`.
- **Outputs:** `mock-interview-{round}.md` (or `-cn.md`), with two sections: transcript and debrief (verdict table, communication feedback, top 3–5 "go back to coach" items, suggested next-round timing).
- **Pairs with:** `qualify-coach` (in a **separate conversation context**).

#### `bullet-writer`
- **What:** Interactive resume bullet writer. Compresses one case into a **Bullet Set** (2–5 bullets) for one Job Family angle. Applies progressive internal logic: HR-readable picture → key design decision → hardest sub-problem → ownership and cross-team impact. Writes the Bullet Set + inline rationale block directly into the master resume.
- **Why:** Bullets are the smallest interview-defensible compression. The B1→B4 progression mirrors how interviewers probe (project picture → decisions → hardest part → ownership). Writing the rationale inline makes the future maintainer of the resume able to understand why each verb/noun was chosen months later.
- **Key files:** `.claude/skills/bullet-writer/SKILL.md`.
- **Outputs:** Edits to `resume.md`. Adds a new `### Bullet Set N, <Company>, <Project> (<angle> emphasis)` section under the relevant experience, plus a `> **Rationale**` blockquote.
- **Pairs with:** `bullet-reviewer` (for JD-targeted fine-tuning); `summary-writer` (which reverse-engineers Summary from Bullet Sets).
- **Gotchas:** Verb register is calibrated by experience level. New grads can't use "Architected", "Spearheaded", "Pioneered" — they signal a seniority the student doesn't have, and the wrong verb collapses at the first follow-up.

#### `bullet-reviewer`
- **What:** Plays a critical hiring manager for a specific target JD and reviews one Bullet Set already in the master resume. Produces before/after fine-tuning suggestions (keyword swaps, emphasis reorder, transferability hints) and, on approval, **directly edits the master**: either in-place for small tweaks (Mode A) or by appending a new JD-targeted variant Bullet Set for larger changes (Mode B).
- **Why:** A general-purpose Bullet Set written by `bullet-writer` is the default; JD-specific tailoring is the rare high-stakes case. Keeping the reviewer as a separate skill lets students tailor without re-writing.
- **Outputs:** Edits to `resume.md` (Mode A in-place, Mode B new variant).
- **Pairs with:** `bullet-writer`.

#### `summary-writer`
- **What:** Interactive Summary writer. Produces one 2-line positioning statement for one Job Family direction, **reverse-engineered** from Bullet Sets already in the master. Drafts an Identity + Strength + Evidence Summary, iterates, and on approval edits the master to append a new Summary Variant.
- **Why:** Summary is a label that points at evidence; without bullets already in place, the Summary has nothing to point at. The reversed order (bullets first, summary after) prevents aspirational vague summaries.
- **Outputs:** Edits to `resume.md`. Appends `### Variant <letter>, for <Job Family> roles` under the Summary section + rationale blockquote.
- **Pairs with:** `summary-reviewer`; requires `bullet-writer` to have run first.

#### `summary-reviewer`
- **What:** Plays a critical hiring manager for a specific JD and reviews one Summary Variant already in the master. Produces keyword swaps, Identity sharpening, tech-list reordering. On approval edits in-place (Mode A) or appends a new JD-targeted Variant (Mode B).
- **Why:** Same logic as `bullet-reviewer` — general-purpose Summary is the default, JD-specific tuning is the optional refinement.
- **Outputs:** Edits to `resume.md`.
- **Pairs with:** `summary-writer`.

## Conventions

### Naming
- **Chinese vs English files:** `-cn.md` suffix marks Chinese content; plain `.md` (or English content inside `.md`) is English. SKILL.md frontmatter is **always English** regardless of body language. Example: `case-cn.md` (Chinese body) vs `case.md` (English body); `SKILL.md` (always English frontmatter, body language matches `examples/<lesson>/README.md` convention).
- **Time-prefixed experience folders:** `from-YYYY-MM-to-YYYY-MM-<company>-<topic>/` under `students/<name>/experiences/`. The time range is part of the path so experiences sort chronologically without metadata.
- **Qualify-for sub-folders:** `qualify-for-<Company>-<Role>/` nested inside an experience folder. One per JD targeting. Holds the full 6-stage pipeline output for that specific JD.
- **Skill prefixes:** `qualify-*` = stages of the elevation/from-scratch pipeline. `mini-project-*` = case design and review. `bullet-*` and `summary-*` = resume output. `lesson-smith-*` = curriculum maintenance. Prefixes encode pairing relationships (writer/reviewer, design/review) and pipeline membership.

### Skill structure
- Every first-class skill has `SKILL.md` plus often `references/` and `templates/` subdirectories. `references/` holds long-form rules and rubrics; `templates/` holds boilerplate files the skill substitutes placeholders into.
- Skill frontmatter is YAML and always English: `name`, `description`, `allowed-tools`, `argument-hint`.

### Severity convention
- 🔴 **Core** — blocks the phone screen. Must be fixed before applying.
- 🟡 **Important** — weakens the on-site. Should be fixed if time permits.
- 🟠 **Nice-to-have** — polish. Can be skipped without losing the interview.
- Used consistently across `qualify-gap-analyze`, `qualify-execution-plan`, `qualify-coach`, `qualify-mock-interview`, `mini-project-review`. Do not translate to P0/P1/P2 (loaded terms) or High/Med/Low (generic).

### Verb registers (calibrated by experience level)
- **New grad:** "Built", "Designed", "Implemented", "Wrote", "Studied", "Investigated". Forbidden: "Architected", "Spearheaded", "Pioneered", "Led a team".
- **Mid (1–5 yr):** Above + "Owned", "Refactored", "Migrated", "Led" (small team, scoped).
- **Senior:** Above + strong verbs when the case backs them up.
- Enforced in `bullet-writer` and `bullet-reviewer`.

### No first-person in resume content
- Bullets and Summary are written third-person with the subject implicit: "Built a BI agent" not "I built a BI agent". The chat / rationale blocks may use first-person.

### Inline rationale blockquotes
- Every Summary Variant and (optionally) Bullet Set in the master ends with a `> **Rationale for this Variant** / **Bullet Set**` blockquote explaining verb choices, noun choices, identity choices, and tech-list ordering. Survives revisions and lets mentor reviews comment directly on the rationale.

| Dependency | What it's for | Why chosen |
| :--------- | :------------ | :--------- |
| `mise` | Tool-version management + task runner. | One config for both "which Python?" and "what commands?". Replaces `pyenv` + `make`. |
| `uv` | Python virtualenv + package manager. | Fast and Cargo-style. Installed via `mise`. The empty `uv.lock` confirms zero runtime deps. |
| Python 3.12 | Future-proof runtime for any automation that gets added. | Newest stable when the project was started. **WHY (best guess; verify with project owner):** also matches the Python ecosystem the curriculum's audience is most likely to target. |
| Claude Code | Runs the agent skills. | The 10 first-class skills are written against Claude Code's skill format. |
| Markdown | All teaching content, all artifacts. | Plain text, git-friendly, renders in GitHub. The skill outputs assume markdown. |

There is no `requirements.txt`, no `package.json`, no Docker. The project deliberately stays close to plain text and prose.
